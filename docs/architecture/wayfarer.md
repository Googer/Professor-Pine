# Wayfarer: export, import and review

The true list of gyms from Wayfarer: the export file and its parts, S2 cells and the area of an export (Pine's internal package `@pine/wayspot-core`, `packages/wayspot-core/`), matching gyms to Wayspots, the import (`/gym import`) and the review queue (`/gym review`). Read before changing the export format, the matching or the import and review commands.

## The export file

- The Wayfarer export (`packages/wayspot-core/src/export-file.ts`, written by the Pine Wayspot export tool, read by the bot; version 1 pinned by `packages/wayspot-core/fixtures/export-v1.json`, which the tool's own tests read too) is `WayspotExport`: `format: 'pine-wayspots'`, `version` 1, `script`, `startedAt`, `finishedAt`, `regions` (the KML's area names), `outlines` (their outlines, in that order, closed rings; required, no format version for it: a file without them is `no-outlines`, saved by an older version of the tool), `margin` (metres the run went beyond the outlines, 0 to `MAX_SCAN_MARGIN`), `cells` (level-14 tokens received whole), `bareCells` (received empty; both count as covered: `coveredCells`, but an empty cell that a Wayspot of the file lies in, whatever made the file (one run, its parts merged, a run kept before the rule): content wins over empty, plan 8W-3), `wayspots` (`ExportedWayspot`: `id` of Wayfarer's form, `isWayfarerId`; `kind` `gym | stop | powerspot`; `status`, acted on only by `withGameKinds`, which `/gym import` applies once a file is read: a stop Wayfarer has as `INACTIVE` is a Power Spot, an inactive Power Spot stays one (Matt, 2026-11-02); `lat`, `lon`, `title`, `address`, `description`, `image`, empty where Wayfarer has none), and `part` for a file of an export saved in parts. `readWayspotExport` checks everything (`ExportProblem`: `not-json`, `not-an-export`, `version`, `too-many` beyond `MAX_EXPORT_WAYSPOTS` / `MAX_EXPORT_CELLS`, `bad-wayspot` with its index and `WayspotFault`, `bad-cell`) and uses nothing of a file that fails; of several Wayspots with one id the last counts. `writeWayspotExport` writes one line with the keys in a fixed order. The file is gzip (`pine-wayspots-<date>.json.gz`); `/gym import` also takes plain JSON (`unpackExport`: gzip by its first bytes, `MAX_UNPACKED_BYTES` 64 MB, UTF-8).
- An export larger packed than `MAX_PART_BYTES` (9 MB; Discord takes 10) is saved in parts: `exportParts(file, count, runId)` cuts the cells in token order (neighbours stay together) into parts of about equal weight, each a whole export of its own cells and the Wayspots that lie in them, with `part: { index, count, runId }` (`count` 2 to `MAX_EXPORT_PARTS` 5; `runId` names one saving of one run, `run-<run id>-<saved at ms>`); the tool names the parts `pine-wayspots-<date>-part<n>of<m>.json.gz`. `/gym import` takes `file` and `file2` to `file5` (`FILE_OPTIONS`), checks every file's size (`MAX_EXPORT_BYTES`) before it downloads any, names the file a refusal is about when there are several, and merges with `mergeExportParts` (`PartsProblem`: `not-parts` for a whole export beside other files, `mixed-runs`, `same-part`, `missing-parts`); merged, an export has no `part`, and a cell read empty in one part and whole in another is whole.

## Cells and the area

- S2 cells are `packages/wayspot-core/src/s2.ts` (pure, `bigint` ids, checked against known cells): `cellIdAt(point, level)`, `cellToken` / `cellIdOf`, `isWayfarerCell` (a level-14 token written as S2 writes it), `wayfarerCellAt(point)`, `cellCentre(token)`, `WAYFARER_CELL_LEVEL` 14. Whether an export covers a place is whether the token of its level-14 cell is in `coveredCells`.
- The area of an export is its outlines grown by its margin (`packages/wayspot-core/src/scan-area.ts`; Matt, 2026-10-15: an outline drawn "into the void" may leave out a gym its admin thought was in, and what lies just outside is how they find out): `scanArea(outlines, margin)` (`box`, `contains`: inside an outline or within the margin of one, `nearRing`), `DEFAULT_SCAN_MARGIN` 500, `MAX_SCAN_MARGIN` 2,000, `isScanMargin`; `areaCells(outlines, margin)`, every level-14 cell of the area once, found as the cells of points 300 m apart (a cell that reaches into the area by a sliver only may be left out), and `missingCells(outlines, received, margin)` those not received: an export is finished when none is missing (`scanFinished`, below). Fixtures for both repositories: `fixtures/export-v1.json` (and `.json.gz`) and `fixtures/import-report.csv` (made by `importReportCsv`, checked by `src/render/wayfarer-report.contract.test.ts`), exported as `@pine/wayspot-core/fixtures/…`.
- The export is made by the Pine Wayspot export tool, a separate, private tool that the owner's Pine instance hands out to approved admins (`docs/web-setup.md`); `/gym import`'s help names where to ask for it (`settings.wayspotTool`). The Wayspot export tool's part of this file is kept with the tool.
- The tool imports these modules of the package: `export-file`, `s2`, `lat-lon`, `distance`, `region-membership`, `kml` and `scan-area`, and reads its fixtures in its tests: `export-v1.json` and `.json.gz`, and `import-report.csv`, the report of `/gym import` (`src/render/wayfarer-report.contract.test.ts` pins the file; `fixtures/README.md`). What these modules export, and the two files, are an interface of the tool: a change to them, or a fixture made anew, is checked against the tool (its `npm run check`, with this checkout beside it) before it is kept.

## Matching and the import

- Matching gyms to Wayspots is pure (`src/domain/wayspots/match.ts`, `matchGyms(input): ImportPlan`): by id (a `pogoId` that is a Wayfarer gym of the file; beyond `CANDIDATE_METRES` 100 m it is asked about instead of moving the gym; of two gyms that hold one id the nearer to the Wayspot is it, ties to the lower id, and the other shares it (plan 8W-3): it goes on as a gym never matched, and if nothing takes it it is asked about with that Wayspot as its own candidate marked `heldBy` the nearer gym, a `missing` item unless a Wayfarer gym near makes it a `match`; such a candidate has no "Same as" or "New gym", and `/gym review` says "<gym> shares its Wayspot **T** with <holder>, which lies nearer to it: that gym is the Wayspot now.", however far it lies, and for a Wayspot that is a PokéStop or Power Spot now "… shares its Wayspot **T**, a PokéStop now, with <holder>, which lies nearer to it and holds it too."), then certain among the Wayspots not taken, exactly one by `certainBy` (title equal by `nameKey` within `CERTAIN_NAME_METRES` 20, equal but for "the", "a", "an" and punctuation by `looseNameKey` within `CERTAIN_LOOSE_METRES` 50, any title within `CERTAIN_PLACE_METRES` 5 for a Wayfarer gym only; a gym marked "not in Wayfarer" only by id or name), or exactly one by name beside others by place alone (`certainPick`), every pick by name before any by place alone (a pass takes picks by place only when it has none by name), within each the gyms ordered by the Wayspot each would take, nearest first, and again while a pass takes anything (never a gym whose Wayfarer id the file lacks where it did not cover every cell within `COVERED_AROUND_METRES` of it, plan 8W-3: that Wayspot is there, unseen, maybe across the edge of the gym's cell; such a gym is `notCovered` with the first uncovered cell, and `isOtherWayspot` reads the same); a Wayspot goes to at most one gym, and the Wayfarer ids of gyms outside the input are taken. A Wayfarer gym nobody took is offered to a gym within 100 m that may be it (neither matched nor marked; not one whose Wayfarer id the file lacks where it did not cover the gym's cell, which is a Wayspot the file did not see; not one whose last answer was "None of these" about that Wayspot, `MatchInput.refused`, from `latestDecided`), its namesake first, else the nearest, each gym at most `MAX_CANDIDATES` such Wayspots with its own first (the rest go to the next such gym; when every gym that may be it has its five, it is neither offered nor added but `held`, and a later import offers it once a place is free); with none it is added where it lies in the regions, unless a gym outside the input that may be it (`MatchInput.others`, `isOtherWayspot`: not marked, and its id neither a Wayfarer gym of the file nor absent where the file did not cover it, and its latest decided item of any server, `latestDecided('any', ...)`, not "None of these" about that Wayspot) lies within 100 m: then it is `held` too (counted in the preview, "N Wayfarer gyms wait for a question about a gym nearby", logged, listed in the report, not added); stops and Power Spots are never added. The rest is queued (`ReviewItem`) with up to `MAX_CANDIDATES` 5 candidates within 100 m (never a Wayspot the plan adds: it becomes a gym of its own): `match` when a Wayfarer gym is among them, else `missing` (its own Wayspot is a stop or Power Spot now, or its id is gone from a covered cell) or `unknown` (never matched, cell covered), a gone id and `unknown` only where every cell within `COVERED_AROUND_METRES` 50 of the gym is covered (`cellsAround`: its point and eight points that far; a gym whose own Wayspot was seen as a stop or Power Spot is `missing` whatever the coverage); a gym in an uncovered cell, or near one, is otherwise `notCovered` (with the first uncovered cell), a marked one counted. A candidate keeps Wayfarer's address (`ReviewCandidate.address`, absent where Wayfarer has none and on items stored before 8W-3), which "Same as" and "New gym" write instead of asking Google (an older item falls back to the kept Wayspot's address). A match writes `pogoId`, the title as name (`newGymName`, tidied by `gym-text.ts`; a blank or too long title leaves the name), the picture (`pictureOf`, at most `MAX_PICTURE_ADDRESS`), and the place when farther than `MOVE_METRES` 3 (`matchChange`). A Wayfarer gym outside the regions that no gym took (here or elsewhere), none is offered and none may be (of the input or of `others`), that lies in no region of another server (`mayPlace`), within the file's margin of an outline (`MatchInput.nearOutline`), is listed in `outsideGyms` (`OutsideGym`: metres from the nearest outline and that region's channel), never added; stops and Power Spots outside are not listed. `withAnswers` leaves out what staff answered already (`stillAnswered` with the new file's covered cells, plan 8W-3: a Wayspot answered about whose cell the new file did not cover is not missed, so that two files covering different cells around a gym do not ask again; a Wayspot new to the question is a change wherever it lies). The CSV of the preview is `importReportCsv` (`src/render/wayfarer-report.ts`, one line per gym, per added Wayspot, per `held` one (with the gym that holds it back where the server may name it: the considered gyms and `WayfarerPreview.holders`, the gyms outside the import it may touch; else no gym) and per `outside` Wayfarer gym, the last with its metres and the nearest region's channel name in the column `region`, empty when the bot does not see the channel).
- The import is `ctx.wayfarer` (`WayfarerImportService`, `src/services/wayfarer-import-service.ts`): `preview(staff, file)` plans and writes nothing; `apply(staff, file)` plans again inside `GymAdminService.batch` against the gyms as they are then and writes that plan, each gym's write decided before any of it is written (`mayPlace` first: a match that would move a gym where the server may not put it is held and asked about); each match is one row write (a move takes the other fields as its `patch`: a move refused when the regions changed meanwhile writes nothing, and the summary counts a rename only with its move); a write that fails is counted and logged, and the import goes on; a move over `REFETCH_METRES` 25 takes the Wayspot's address and has its places fetched again, in `GymUpkeep`'s line (`placed(id, { places: 'later', address })`; its address too when the Wayspot's names no street); the outcome says what was not recorded (`Unrecorded`). It considers the gyms this server may touch (`mayTouch`) that lie in its regions, and gyms in no region of any server that lie within 100 m of one of its outlines (`nearRing`, `region-membership.ts`) or in a covered cell; Wayspots outside the regions count only near those gyms. The count `outside` (preview and outcome: "N Wayfarer gyms lie just outside every region of this server: your outlines may leave them out") is `plan.outsideGyms`, measured by `metresFromRing` (`region-membership.ts`, beside `grownBox`) against the server's outlines within `file.margin` (none for a file without a margin); the `ignored` Wayspots may include them. `GymAdminService.batch(place, source, work)` runs `work(ops)` under the admin lock with `GymBatch` (`add`, `addBlock`, `move` with an optional `patch`, `update` of `BatchPatch`, `remove`), none of which takes the lock or announces: what it changed is announced in one summary at the end, also when `work` failed (`source` decides when it is posted: gathered for the review, at once otherwise; the summary names no source, Matt, 2026-10-16); work that asks for the lock from inside never finishes. `delete(id, by, place, onlyIf)` asks `onlyIf` under the lock first and answers `withdrawn` when it no longer holds.
- The new gyms of an import are added in blocks of `IMPORT_BLOCK` 250 (plan 8W-6; a city's first import adds thousands, which one by one held the lock and `/gym` for minutes): `GymBatch.addBlock` decides each gym first as `add` does (`foreign`; `near` a gym not among its `knownNearIds`, the import's matched, marked and added gyms; the gyms of the block are known to each other, as the gyms an import added one by one always were: two Wayfarer gyms within 10 m of each other are both added), then writes those accepted in one transaction with the nearest gyms worked out once for the block (`GymStorage.createBlock`, `nearestBlockChanges` of `src/domain/gyms/nearest.ts`: each new gym's nearest among all, and every other gym the block's nearest where it is nearer; the nearest-gym scan once per block, not per gym), then reads them into the directory in one turn (`GymDirectory.refreshGyms`) and puts them and the gyms whose nearest gym changed in the line once (`GymUpkeep.placedBlock`). A gym refused is reported as before (`held`, logged) without failing its block; a block whose transaction fails left nothing and is added gym by gym (`failed` for a gym that cannot be written, logged). The lock is held across all blocks, and each block is a line in the log (`a block of Wayfarer gyms was added`: which of how many, and its gyms added, held and failed), by which staff follow a first import. One list of the gyms they may stand beside serves a whole block. Matches, the review queue, the kept Wayspots and the summary are as before. Tests: `MemoryGyms.blocks` counts the blocks written, `refuseNames` has a write refuse a gym by its name.
- `/gym import` (`src/commands/gyms/import.ts`) previews in a v2 message (counts in sentences, by region, the stops of Pine's own within 30 m of an imported stop named for staff to remove, plan 8R-1 `pineStopsNear`, `wayfarer-import.csv` as a file component, Import / Cancel) and keeps the parsed export in its own `pendingImports` (`MAX_PENDING_IMPORTS` 3, `IMPORT_PENDING_MINUTES` 30) under the token of `gym:<token>:wayfarer-import|wayfarer-cancel`, only what Import reads of it (`forImport`: no descriptions, no status; plan 8W-3); an export that would change nothing gets no Import (`changesNothing`; an item counts as queued already, `queuedAlready`, only when an open item asks the same kind about the same set of candidate ids; a preview that could not read the kept Wayspots may change them: it offers Import and says why it cannot tell, `KEPT_UNREAD`). The sentences of the preview, the outcome and the question are cut by `sentencesText` (`cutMarkdown`: never inside a mention, a code span or bold). Import replaces the preview with "Importing…", then the outcome, or a failure line when `apply` throws; when that edit fails (an import may outlast the interaction) the outcome is logged.
- The scanned area of an export is its own outlines grown by its margin, never the server's regions of the day (`src/domain/wayspots/scanned-area.ts`): the preview says where they differ (`compareOutlines`: regions not as scanned, areas that are no region now) and lists the gyms this server may touch that lie in no region of any server beyond the area (`gymsBeyond`, `WayfarerImportService.outsideArea`, the report's `beyond`). After an import of a finished scan with a margin (`mayDeleteOutside`: every cell of the area received, `scanFinished`) whose outlines are every region of the server as it is now (while `compareOutlines` names a region not scanned, `outsideArea` gives nothing and the preview says why), the outcome offers "Delete N gyms outside the area…" (`gym:<token>:outside-ask`, then `outside-delete` / `outside-keep` of a private question naming the first `OUTSIDE_NAMED` and what goes with them; the area alone is kept in `pendingOutside`, the question under `questionToken` of the outcome's token, so that asking again replaces it and presses do not crowd the store; it names each gym's metres from the nearest outline, as the report's `beyond` lines do): the list is worked out again at each press (the question and the deletion, under the lock, refuse with nothing deleted when a region was added or changed since: `OutsideDeletion.regionsNotScanned`), each gym deleted through `GymBatch.remove` (gym administration's deletion under the batch's lock; an active raid keeps its gym, named), one summary at the end (`deleteOutside`).
- An imported gym takes the Wayspot's address (`wayfarerGeodata`, `src/domain/geo/wayfarer-address.ts`: Wayfarer's address read as Google's address parts, a plus code dropped, null without a street), as does a matched gym without an address or moved beyond `REFETCH_METRES`; Google is then asked for its places only (`GymUpkeep.placed(id, { places: 'later', address: false })`, `GymBatch.move(…, { address })`). What waits for Google is a line in the database (`GymLookups`: `GymLookupRepository`, table `GymLookup` of migration 014 with its `regionRank` of migration 032; twin `MemoryGymLookups`; both run `gymLookupCases`; plan 8W-6, `gyms-and-regions.md` for the budget and the ranks): gyms by the rank of their best region, then by the time queued, one every few seconds, one at a time (a gym stays in the line while it is asked about, and one put in it again before its turn is written down keeps its row), each question counted by itself when it reached Google, and one whose geocode did not answer kept waiting for its address (to the end of the line); while Geocoding is refused (`denied`) a gym that waits for its address asks no Places (each is billed) and keeps its place in the line, and the line goes on with the gyms that wait for their places alone (`GymLookups.next({ placesOnly })`), waiting out the refusal only when every gym left waits for its address, and in either refused path an address asked for again during the turn keeps waiting (plan 8W-3); its upsert uses MySQL's row alias (`INSERT … AS new`), never `VALUES()`, deprecated since 8.0.20, as do the Wayfarer tables' (`lastWarnings` in their database tests); taken up at start (`resume`); a gym added or moved by hand is still asked about at once, and counted.

## The kept Wayspots

- Every Wayspot of an applied import is kept (plan 8W-2): table `Wayspot` (migration `2026_10_16_017_wayspot`; a migration merged after it must sort after it, since Kysely refuses an earlier name once 017 ran on a database: 8H's is `2026_10_16_018_party_history`, 016 stays unused; first merge wins, the second renumbers above it, and only a merged migration, or one that already sorts after everything merged, is run on the dev database. The table: the Wayfarer id, `kind`, `formerKind` (the kind before an import last saw it as another; `stop` for a promoted stop), place, title and address plain (not entity-encoded: nothing legacy reads it; cut to 255), picture (`pictureOf`, the address as Wayfarer gives it; a message shows it through `wayspotPicture`: https, `=s400`), `firstSeen` (when an import first kept it: the import's time), `lastSeen` (when the scan of the newest file that saw it was made, `scanTimeOf`: the file's `finishedAt`, else `startedAt`, else the import's time, never later than the import's time: a file dated in the future would freeze its rows); not per server) behind `WayspotStorage` (`WayspotRepository`: `all`, `gone`, `saveFromImport({ upsert, remove, gone }, importedAt, scannedAt, startedAt)` in one transaction of chunks of 500, `remove(ids)`; twin `MemoryWayspots`, both run `wayspotCases`). The pure part is `planKept` (`src/domain/wayspots/keep.ts`, rows `kept.ts`): every Wayspot of the file but those whose id is a Pine gym's `pogoId` (of any server) after the import, which live in `Gym` (a row of one is deleted); a kept row not in the file is marked gone where the file covered its cell (`coveredCells`; plan 8W-3: the row stays with `kind` `gone`, its kind before in `formerKind` and its `lastSeen` the time of the scan that found it gone, never read by `all`; no column was added, ruling: tombstones are kept for good, a few thousand rows at most: nothing prunes them, and every preview and import reads them all, `WayspotStorage.gone`, with the kind each had, `GoneWayspot` (a stop where it is not known, `UNKNOWN_GONE_KIND`, so that no tombstone is left out); one brought back keeps that kind as its `formerKind`, and a Wayfarer gym added that was such a stop counts as one, `promoted`), and a Wayspot a newer scan found gone (`KeptInput.gone`, from `WayspotStorage.gone`) is not brought back by an older file (a newer one brings it back, keeping its `firstSeen`); the storage keeps these guards itself whatever the caller planned (plan 8W-3: an upsert never overwrites a row, kept or gone, last seen after the file's scan, by MySQL's row alias `AS new` with `IF(Wayspot.lastSeen > new.lastSeen, …)`, `lastSeen` assigned last; a row is marked gone only when not seen since the file's scan started, or at its own scan time), so that imports that were not one after the other cannot undo each other either; a row last seen after the file's scan (another server's newer scan) is neither changed nor deleted nor counted (a week-old file does not undo a fresh scan; only a gym that is it now takes it), and one another scan saw after the file's scan started (`scanStartOf`: `startedAt`, else `finishedAt`, never later than the import) is not deleted (a row last seen exactly at the file's scan time is its own: an earlier import of the same scan); moves and renames are silent; `WayspotCounts` counts stops and Power Spots `added`, `changed` (kind, title, place, address or picture), `gone` (also a stop that became a gym), and `gyms` (kept Wayfarer gyms written, said nowhere and no reason to offer an import). The import reads the kept rows under its lock, writes them after the gyms (`Unrecorded` `wayspots` when it fails or they cannot be read; the gyms stand, and a gym added is then not known to have been a PokéStop) and stores the counts in its row as `wayspots*`; preview and outcome say them in one line (a preview that cannot read them logs it and says nothing of them), and an import that changes only stops and Power Spots is offered (`changesNothing`, `changesWayspots`). A Wayfarer gym whose adding failed stays a kept `gym` row. A review's Same as (`applyMatch`) and New gym delete the row of the Wayspot the gym now is; New gym gives the gym the kept row's picture. A Wayfarer gym added whose kept row was a stop (`wasStop`) is counted by `GymBatch.add(…, { promoted: true })`: the summary says "Professor Pine has added 12 gyms (3 of them were PokéStops)". The summary also says what the import changed of the stops and Power Spots (`planKept`'s `byKind`, `WayspotChanges`, given to the batch by `GymBatch.countWayspots` once they are written), each count by its kind: "It also added 120 PokéStops and 3 Power Spots, changed 4 PokéStops, and removed 2 Power Spots."; its `gone` is only what left Wayfarer's map, not a stop that became a gym (unlike `WayspotCounts.gone`, which the preview says): a stop Wayfarer now shows as a gym, taken by a Pine gym or not, is counted neither as removed nor as a stop. Its `changed` is only a new kind, a new title or a move over `NOTICED_MOVE_METRES` 10 (`noticeable`): a new address or picture alone is written but not said, so that routine re-imports post nothing (the preview's `changed` still counts them). An import that changed no gym posts nothing at all, its stop and Power Spot counts said only in its answer (8W-3, plan 8F-1). - The places Google gave around a PokéStop or Power Spot (plan 8W-6) live in a table of their own, `WayspotPlaces`, keyed by the Wayspot's id with the point and kind they were asked for: the import's upsert of `Wayspot` neither reads nor clears them; a Wayspot moved by more than a few meters or of another kind waits in the line again, and one that became a gym or was found gone loses them (`gyms-and-regions.md`, the line).

## The review queue

- A file of sponsored gyms seeds the mark before a server's first import (`npm run gyms:seed -- <file> --server <id> [--apply]`, `./pine seed-gyms`; `src/ops/gym-seed.ts`, the pure part `src/domain/gyms/seed.ts`): a CSV of `gym,id,name,lat,lon,region,basis` (`GYM_SEED_COLUMNS`). A row with `gym` marks that gym, and is `wrong` (exit 1, the rest still done) where there is no such gym or it lies beyond `GYM_SEED_SAME_METRES` (100) of the row. A row without adds a gym with `id` as its `pogoId` and marks it (`notInWayfarerBy` `gyms-seed`), through `createBlock` and `nearestBlockChanges`, unless a gym holds that `id` (that gym is marked: so a second run adds nothing), the row lies outside every outlined region of the server, or a gym or an earlier row lies within `DUPLICATE_METRES`. It writes no address or picture: the bot's next start puts the new gyms in the line for Google. A dry run without `--apply`. Pittsburgh's file is kept out of the repository; the tests use `test/fixtures/sponsored-gyms.csv`, made up.
- The review queue is `GymReview` behind `WayfarerStorage` (`src/db/repositories/wayfarer-repository.ts`; also `GymWayfarer`: `lastSeen` and the mark "not in Wayfarer", and `WayspotImport`: who, when, counts), with `MemoryWayfarer` (`test/support/wayfarer.ts`) as its twin and `wayfarerStorageCases` (`test/support/wayfarer-cases.ts`) as the behaviour both run. One open item per gym (`openGymId`, unique); `saveReviews` refreshes an open item and keeps its `queuedAt`; every method reads and writes only the given server's items; candidates are JSON (`readCandidates`, `ReviewCandidate`, the gym's own Wayspot flagged `own`); an item keeps the gym's `pogoId` when it was queued (`gymPogoId`, `QueuedReview`), and once it differs (another server's import matched the gym) the item waits for the next import: `next` passes over it without closing it, and every answer but Skip is `changed` with `waits`. "Keep" and "None of these" stick until Wayfarer changes (Matt, 2026-10-15): an import does not queue a gym again while its latest decided item (`latestDecided`) has that answer with the same kind and the same set of candidate ids (`stillAnswered`, `src/domain/wayspots/review.ts`); those gyms are counted as `answered`.
