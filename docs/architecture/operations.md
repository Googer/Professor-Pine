# Operations

How Pine runs: the Docker stack, the image, the operator script `./pine`, the bot's health and its alerts to the owner, the watchdog, backups and restore. Read before changing `Dockerfile`, `compose.yaml`, `pine`, `docker/` or `src/ops/`.

## The rule

- A host needs Docker (with Compose) and git, nothing else: no Node, npm or MySQL client. Every operator step is `./pine <command>`, a POSIX `sh` script at the repository root that wraps `docker compose`; it runs on Debian (dash), on macOS with OrbStack (`docs/guides/macos-host.md`) and in Git Bash on Windows (Docker Desktop). It uses only what every such shell has besides (`gzip`, `tail`, `tr`, `sed`, `basename`, `dirname`, `id`). A step that would need anything else on the host is wrong.
- The script is checked with `shellcheck -s sh` (the `koalaman/shellcheck` image) and kept LF by `.gitattributes`, as is every `*.sh`. It exports `MSYS_NO_PATHCONV=1`, so Git Bash leaves container paths (`/pine/backup.sh`) alone. A command is a function `cmd_<name>` (a hyphen is an underscore) plus a line of `usage`; nothing else needs to know of it; the dispatch is a function, read whole before `update` replaces the file. Each command says what it does and runs Compose through `run`, which prints the command first; errors are plain sentences through `fail`; a command that stopped the bot and then fails says "The bot, its watchdog and the backups are stopped: './pine up' starts them again." (a restore whose load the bot would refuse says that instead) A path the operator gives (a dump) is read from where they ran the script.
- The commands that log the bot in to Discord are `up`, `restart`, `update`, `restore` (when it starts the stack) and `deploy-commands`; `emoji-upload` contacts Discord through its REST API (its dry run lists the application's emoji, `--apply` uploads), and `cutover-check` reads it with the token; `migrate`, `backup`, `restore --no-start`, `role-auth-export`, `status`, `logs`, `down` and `shell` do not. `restore` starts the stack only on a terminal or with `--start`.
- The installation's own files are git-ignored and beside `compose.yaml`: `.env` (secrets) and `pine-settings.json` (the settings, made from `data/settings.json`, or from a legacy installation by `./pine convert-settings`). `./pine` refuses to run without either and says how to make them; the repository's `data/settings.json` is never the installation's, so `update` finds no change of its own. `pine-settings.json` is mounted as a single file: an editor saves by writing a new file, which a running container never sees, so an edit needs `./pine restart` (and `./pine restart backup` for the backups' time zone). `PINE_ENV_FILE`, `PINE_SETTINGS` and `COMPOSE_PROJECT_NAME` give a second stack on the same machine its own files, volumes and image (`professor-pine:<project>`) (a rehearsal, a scratch stack). The project's name is Compose's to resolve and `./pine` never sets it: the shell's `COMPOSE_PROJECT_NAME`, else the one in the env file (a rehearsal's `.env` names itself there), else `pine` (the `name:` of `compose.yaml`). Were the script to set it, it would outrank the env file and a rehearsal's `restore --replace` or `down` would act on production.
- `PINE_TOOL_DIR` (blank: `./wayspot-tool`, git-ignored and kept out of Docker's context) is the folder of the Wayfarer export tool on the owner's instance (`web.md`, "The Wayfarer export tool"): every container of the bot mounts it read-only at `/app/wayspot-tool`, empty on any other instance (an empty folder serves nothing). `./pine`, before every command that needs the stack (`make_tool_dir`), makes the folder when it is missing, readable and searchable by others whatever the umask (`chmod a+rx`; so that Docker does not make it as root, and the owner's deploy can write into it), and refuses nothing there (it warns when the folder cannot be made). Only the commands that start the bot (`up`, `restart`, `update`, and `restore` when it starts the stack, before anything is stopped) check it, beside `check_legacy_parties` (`check_tool_dir`): a path that is no folder, a folder others cannot read and search (`find -perm -o=rx`), or one of the two files the bot serves, `pine-wayfarer-export.user.js` and `CHANGELOG.md`, that others cannot read (`-o=r`), is refused, named; other files there (a deploy's dotfiles, its `.tmp`) are not looked at. The bot runs as the image's `node`, most likely not the folder's owner, so what the operator may read says nothing. The private repository's deploy leaves its files readable by others (mode 644). No shell test covers these checks (none of `./pine`'s checks has one); they were tried in a `node:24-slim` container (before Node 26) as the user `node` under umask 077 (a missing folder made 755, a 750 folder refused only by the starting commands, a dotfile and a `.tmp` of mode 600 passed, either served file of mode 600 refused).
- Every build of the bot's image (`up`, `update`, the one-off commands, `convert-settings`) runs with `--pull`: Docker otherwise keeps the `node:26-slim` it first fetched and builds on a Node without its later security releases (2026-10-22: 24.21.0 kept while 24.22.1 fixed a Brotli remote code execution). A build therefore needs the network; when nothing is newer the pull costs a second.
- `./pine update`, in this order, nothing changed until the backup is made: it refuses a clone with changes of its own and a branch without an upstream; `git fetch`, and nothing more when there is nothing new; the database is checked and, if it has tables, a verified backup is made through the stack as it runs now (a pulled change may upgrade MySQL or migrate the data); a failed check or backup stops it, nothing changed. Then `git pull --ff-only`, the newest MySQL and tunnel images of their tags (`pull --ignore-buildable`), the build, `up -d`, and the backup service and the watchdog recreated (they run what the checkout mounts). A failed build or start after the pull says "The code is updated but the stack still runs the old version: './pine up' builds and starts it."; `./pine up` also finishes an update that stopped there (a second `update` finds nothing new).

## The image

- `Dockerfile`: multi-stage on `node:26-slim`. The build stage runs `npm ci --ignore-scripts` (the workspace `packages/wayspot-core`'s `package.json` copied first: the lock file names it) and `npm run build` (the package `@pine/wayspot-core`, the bot, then the web pages' bundle by `scripts/web/build.ts`, which `.dockerignore` lets in; before plan 8W-P it did not, and the image did not build); the runtime stage has the production dependencies (also without install scripts: none is needed for the CPU, as in the checkout), the package's `package.json` and compiled `dist/` (where the workspace link `node_modules/@pine/wayspot-core` points), `dist/`, `package.json` (it says the files are ES modules), the square raid egg pictures `pictures/eggs/` (plan 8D-F: `EGG_FOLDER` finds them beside `dist/` as beside `src/`), the package's `LICENSE` beside its `package.json` (`@pine/wayspot-core` is MIT, unlike the rest of Pine, and its notice goes with every copy; `.dockerignore` lets it in), the icons of the posts' buttons `pictures/emoji/` (plan 8D-G, for `emoji-upload`: `EMOJI_FOLDER`, the same way) and the default `data/settings.json`. onnxruntime-node keeps its library for the image's platform only (`TARGETARCH`: linux x64, or arm64; arm64 is untested). Runs as `node`, `NODE_ENV=production`, `node --enable-source-maps dist/index.js`, `STOPSIGNAL SIGTERM`. About 490 MB unpacked.
- The runtime reads from disk only its settings and what it keeps under `var/`. `.dockerignore` lets in only what the build needs (never `.env`, `var/`, `.git`, `node_modules`).
- `var/` is a volume (`pine-var`), writable by `node` because the image's folder is: the game data cache, map pictures, the square pictures of the stops (`var/pictures/`, plan 8R-6, at most 2,000), the screen reader's models (downloaded at first use) and screenshots, and the health files.
- The one-off commands run in the same image: `dist/db/migrate-cli.js`, `dist/discord/deploy-cli.js`, `dist/ops/restore-cli.js`, `dist/ops/health-cli.js`, `dist/ops/emoji-upload-cli.js`, `dist/ops/role-auth-cli.js`, `dist/ops/history-import-cli.js`, and the watchdog `dist/ops/watchdog-cli.js`. What an operator of an installation runs is such a CLI under `src/` (its logic in a module beside it, tested; the CLI only reads the environment and the arguments), with an npm script for the checkout (`tsx` on the `.ts`) and a `./pine` command for the stack; the tsx scripts of `scripts/` are the developers' and are not in the image.

## The stack

- `compose.yaml`, project `pine`: `mysql` (`mysql:8.4`, volume `mysql-data`, utf8mb4 with `utf8mb4_0900_ai_ci`, healthcheck by `mysqladmin ping` over TCP), `pine` (the bot), `watchdog`, `backup`, and `cloudflared` under the profile `tunnel` (`COMPOSE_PROFILES=tunnel`; the bot's web server on `0.0.0.0` inside the network, `web.trustProxy` on, its port never published, the tunnel's public hostname pointing at `http://pine:<web.port>`, the token `CLOUDFLARE_TUNNEL_TOKEN` from the env file; `docs/web-setup.md`). No service publishes a port.
- `lower_case_table_names=0` (Linux's default, set explicitly; it can only be set when the data directory is made): table names are case sensitive, the bot's are mixed case (`Guild`, `GymMeta`), and a dump of the stack loads unchanged into any server that keeps case (the test containers, another Linux host). A dump from MySQL on Windows has lower-case names; `./pine restore` renames them, and the migrator refuses such a database on a case-sensitive server before writing anything.
- There is no profile for an external MySQL (spec 9.2's is dropped): an instance restores its dump into the stack instead.
- `.env` is read by Compose for the values of `compose.yaml` and handed to the bot (`env_file`). Inside the stack the bot reaches MySQL as `mysql:3306` whatever `.env` says (`DB_HOST`, `DB_PORT` are set by the compose file); `DB_USER`, `DB_PASSWORD`, `DB_SCHEMA` also create the user and the database on MySQL's first start. `DB_ROOT_PASSWORD` is root's and `CLOUDFLARE_TUNNEL_TOKEN` is cloudflared's: both are blanked for the bot. `pine-settings.json` is mounted read-only.
- `pine`, `watchdog` and `cloudflared` run with `no-new-privileges`, every capability dropped, and limits of memory and processes (4 GB and 512, 512 MB and 128, 512 MB and 256; the bot's heap limit stays what it was on an 8 GB VM, tried 2026-11-01): a runaway or broken-into bot cannot starve MySQL or another stack on the host. `mysql` and `backup` start as root and step down, so they keep their capabilities. Every service's log is at most five files of 20 MB (`x-logging`), which a plain Docker host would otherwise keep whole.
- `pine` waits for a healthy `mysql`, runs under `init: true` (tini hands it SIGTERM and reaps the screen reader's process), restarts `unless-stopped`, and has `stop_grace_period: 2m30s`: the shutdown steps of `src/app.ts` have limits that add up to 145 seconds with every optional step, within 150 s, with 5 s to spare (the queued DMs alone twelve seconds; plan 8H added three seconds for the party history's last try of a record that failed; plan 8X-H the catch-up's two, review r1 C4; plan 8R-6 the pictures of the stops' one, taken from the grunts' messages, whose step has four: the reports at stops' three steps are `stopReportSteps` in `src/app-wiring.ts`; plan 8V-1's events forum stops in the events feed's one second, `eventsFeedStep`, and the party clock's step stops it first, so the clock's upkeep draws nothing of it; branch review BR-2). A new step there means checking that sum, and the watchdog's restart (`?t=150`).
- A new install is `./pine up` on empty volumes: the migrator's new-install path creates the schema.

## Health

- No listener: the bot writes `var/health/status.json` every thirty seconds from the start of `startApp` on (`Heartbeat`, `src/ops/heartbeat.ts`): when; the phase, `starting` until the login to Discord begins (`loggingIn`), then `running`; since when the client is connected to Discord or not; whether the database answered `select 1` within ten seconds. Connected means every shard of `client.ws.shards` is `Ready` and Discord acknowledged its heartbeat within three minutes (`gatewayConnected`): never `client.ws.status`, which discord.js sets to ready once and never back. Written whole (a temporary file renamed). The heartbeat stops just before the database pool closes at shutdown.
- `node dist/ops/health-cli.js` reads it and prints one line, its kind first (`healthLine`: `healthy`, `starting`, `stale`, `missing`, `unreadable`, `slow-start`, `gateway`, `database`), and exits 0 or 1 (`healthVerdict`, `src/ops/health.ts`): unhealthy when the file is missing or older than 90 seconds (a stuck or stopped bot), when the database did not answer the last check, when Discord has been away for more than two minutes after the login began, or when the start has taken more than half an hour. A start with a fresh heartbeat is healthy however long its migrations take. It is the healthcheck of `pine` (every 30 s, 3 retries, a start period of ten minutes) and a line of `./pine status`. In rehearsal mode the file has `rehearsal: true` and every line ends with "; REHEARSAL MODE IS ON" (the kind at its start is unchanged, so the watchdog reads it as before).
- `Lifecycle` (`src/ops/lifecycle.ts`) holds the process's signals and unhandled errors from the first line of `src/index.ts` on. A SIGTERM or SIGINT during the start ends it after the step under way, never in the middle of the migrations (`startCheckpoint`, `src/ops/start-stop.ts`), cleanly: no crash marker is left; a repeat only logs that the step is still finishing (Docker's grace still bounds it). After the start a signal shuts down cleanly and a repeat exits at once. An uncaught exception or unhandled rejection during the start ends it with the owner's alert (`could not start`); after the start an exception ends the run after the shutdown, a rejection is logged.

## The catch-up on reconnect

- Plan 8X-H (Matt, 2026-10-23: catch up, not restart; the staging of 8X-G survived two outages, a DNS outage of two minutes and an hour without network, but what failed meanwhile waited for its next interval). Restarting on every reconnect would restart several times a day (Discord asks for routine reconnects), at the cost of a login, posts drawn anew and open dialogs failing; the watchdog's restart after a long outage stays as it is, and so do the heartbeat and the health rules (they say whether the bot is connected now). In production the watchdog restarts after about seven minutes without the gateway, so the catch-up covers outages of about 30 seconds to 7 minutes; on a laptop without the watchdog, any length.
- **When** (`GatewayWatch`, `src/discord/gateway-events.ts`, attached in `configure` before the login): armed by the first ready (the login's own and earlier reconnections never count); the first `ShardReconnecting` while up marks the gateway away (discord.js says it with every try: the later ones change nothing, and none is logged); `ShardResume` or `ShardReady` brings it back. Back for real when it was away 30 seconds or more (`REAL_AWAY_MS`, counted from the shard's last heartbeat acknowledged where that is more than a minute older than the first reconnection, `MISSED_ACK_MS`, the acknowledgement read at that first reconnection, as the new connection's first one can come before its RESUMED and hide it, review F3: a zombie connection, which discord.js gives up some 82 seconds after the last acknowledgement, or a laptop asleep while connected, which reconnects only at wake; Discord asks for a heartbeat every 41.25 s, so at a routine reconnection the last acknowledgement is up to that old and does not count, review r0 B1), when a shard error came meanwhile (counted only while away: a shard error while connected is said but starts nothing, only a reconnection does, review r0 B8), or when it came back with a new session (`ShardReady`: the events of the time away are lost). Then `discord gateway back` at info (`awayMs`, `shardErrors`, `unsaid`, `newSession`); a routine resume is `discord gateway resumed` at debug. What discord.js 14.27 gives (the brief's review read `@discordjs/ws` 1.2.3): ECONNRESET, ECONNREFUSED, ETIMEDOUT and EAI_AGAIN give no shard error and come back with a fresh `ShardReady`, so an ECONNRESET on a live connection (a second away) is a real return with `newSession` true, rightly: the events of the old session are lost (review F7); ENOTFOUND (Windows' DNS outage) gives a shard error every half second and comes back with `ShardResume` (or `ShardReady` after an invalid session). In Docker a DNS outage is EAI_AGAIN: no shard errors at all. One state for every shard: Pine runs one (`createClient` sets no `shards`, discord.js's `shardCount` of 1; Discord asks for more only beyond 2,500 servers), review r0 B9.
- **Shard errors** are said once per kind (`code`, else the message): the first at warn with the error (`discord shard error`), then at most once a minute `discord shard errors repeated` with how many since and the message (`REPEAT_EVERY_MS`, checked as each arrives, no timer); those not said yet are counted in the line of the gateway back, and a kind is said anew when the next outage begins (also one seen while connected, review r1 C5). Before plan 8X-H each was an ERROR line (206 in two minutes, 819 in the hour). An ERROR line stays for what needs a person.
- **What** (`CatchUp`, `src/services/catch-up.ts`, made in `app.ts` once the stops' posts are there): the jobs one after another, each once, in this order: every active post shown anew, paced (`redrawPosts`: it only queues them, one party every 250 ms, `EMOJI_RENDER_GAP_MS`, so the posts are drawn over N × 250 ms beside the upkeep and the feeds' reads, review r0 B10), and every region's summary drawn anew with them (plan 8R-9, B7: a midnight passed while the network was away moves Coming up to Today; one that reads the same is not edited), the upkeep (`PartyScheduler.catchUp`: first the closings the network failed, `PartyService.redoClosings`, `parties-and-posts.md`, hourly as well, since a request can fail without the gateway going away, review r0 B4; then the sweep of ended parties' posts, the summaries, the access, the routes, the spawn and grunt sweeps, the application's emoji and the rest, after one under way; its steps never fail as a whole, so it runs on every catch-up; before the clock runs or after it stopped it runs none and is not owed, review F6), the posts of the stops in the regions' boards (`stop posts`, `StopPostService.catchUp`: every kept post drawn, unchanged ones not edited, and yesterday's whose delete failed deleted again; a turn-over at midnight that failed waited for the next change of period before; plan 8R-9 also tries those deletes at the channel's next draw), the lines of the region channels (`stop lines`, `StopLineService.sweep`: the lines of ended days whose delete failed, deleted again; also tried before the next line is sent, review W2), then the feeds (with the events forum drawn anew right after the events feed, `events forum`, plan 8V-1, where it is made), each only when its last read failed (`catchUp` of `BossFeedService` for the raid and max bosses, `RaidEventService`, `ResearchTaskService`, `RocketLineupService`, `GameDataService`: the read now through its in-flight guard, after one the timer started, and the next scheduled from it; they retry by themselves within 5 to 30 minutes). One catch-up at a time; a return of the gateway while one runs has one more after it, not one each; nothing loops while the network is down. `caught up` at info names what ran, failed again (`could not catch up` at warn for one that threw) and was not owed. At shutdown (review r0 B6) the party clock's step (6 s) closes it, so that it starts no job more, without waiting for the job under way, and waits for the clock and its upkeep, which starts no step more once the clock has stopped (review r1 C3) and whose closings end between parties as the history's sweep does; a feed's read under way (up to 30 s) ends at that feed's own `stop` step, a drawing of the posts of the stops, and the lines of the region channels on their way (they wait for the posts' links), at `posts of the stops`; the step `catch-up` (2 s) after that one waits for the job left (`CatchUp.whenIdle`). The steps' limits stay within the stop's 2m30s (`stop_grace_period`), with 5 s to spare: the party clock's step went from 10 s to 6 s and the direct messages' from 15 s to 12 s (review r1 C4). Not caught up: the events' pages with spawns (read within the hour while an event is on), direct messages that failed meanwhile (`DmSender` drops a failed send, as always: a DM is worth its moment), the lines said in posts and the pings of a movement or a start that failed, the clock's archive warning and the completion question that failed (the clock asks each once; the closing comes all the same, review F8), interactions (Discord's, lost).
- **Logging of an outage:** a failure for the network (`isNetworkError`, `src/services/network-error.ts`: the codes of a lost network and the time limits, also the abort with which @discordjs/rest ends a request after 15 s, `AbortError` or undici's `UND_ERR_ABORTED`, on the error or any cause, and Discord's 5xx, an `HTTPError` of 500 or more, review r0 A1; never a mysql2 error, though its code be a socket's: the database away needs a person, review r0 A2) is a warning in the boss syncs (a feed out of reach or timed out; one it cannot read stays an error), the game data refresh (a download without an answer), the updates of a post or a summary, and the turn-over of the posts of the stops at a change of period (review F5); the sweep says its failures once per sweep. Debug lines say that a boss feed read changed nothing (`raid bosses read, unchanged`, with how many), that the sweep ran (`swept the posts of ended parties`, archived, the forums looked through and those that failed, review r0 A4; the warning of a failed sweep names the first forum that failed besides the count, A3) and that the application's emoji were read (`read the emoji of the application`, how many), so that a catch-up can be followed at debug.

## Alerts to the owner

- `OwnerAlerts` (`src/ops/owner-alerts.ts`) DMs `OWNER_ID` through Discord's REST API with the bot's token: opens the DM channel, posts plain text with no mentions; times as `<t:…:f>`, so Discord shows them in the reader's zone. Not through `DmSender`: it works without the gateway and from an exit path. `send(kind, text)` never throws, gives up after five seconds (one try), logs a failure, and sends one alert of a kind per fifteen minutes; the stamp is taken before the alert goes (a second one meanwhile is held back) and given back when it fails. The bot keeps the stamps in `var/health/alerts.json` (`FileStamps`) so that a crash loop does not spam; the watchdog in the `ops` volume. `ownerAlertsFrom(env)` needs only `DISCORD_TOKEN` and `OWNER_ID`, so it works before the config is read.
- `src/index.ts`: on a fatal end (the gateway closed for good, an uncaught exception, a start that failed after the config was read) the bot DMs `Professor Pine <what>: <first line of the error>`, then shuts down and exits 1 as before. A config error sends nothing (the operator sees it at the console) but is recorded. The gateway's fatal end goes through `Lifecycle.fatal`: a signal during that shutdown starts no second one and exits at once, the error kept. A failed start ends through `afterFailedStart` (`StartStopped`: clean, exit 0).
- A bot that keeps crashing waits before its login: half a minute per restart after a crash within the hour, ten minutes at most (`loginBackoffMs`, `waitBeforeLogin`, through `StartOptions.beforeLogin`), logged; a stop during the wait ends it at once.
- `CrashRecord` (`src/ops/crash-record.ts`): a marker `var/health/running.json` written at every start and removed at a clean shutdown (SIGTERM, SIGINT, also during the start); the error that ends a run is kept in it. A start that finds the marker DMs "restarted after a crash at <time>: <error, or none recorded>. Restart n in the last hour." (the time is the error's, or the last heartbeat's; the restarts after a crash are kept in `var/health/restarts.json`). Before that, a marker of another bot running from the same folder now is no crash (`runningElsewhere`, staging of 8X-H, H1: two bots with one token answer every interaction twice, each from its own parties in memory): its process is alive, is not this one (a container's bot is process 1 at every start) and showed life within 90 s (a heartbeat of the same process, or its start before the first one, so a crashed bot whose number another process took does not count); the start then logs `another Pine is running from this folder: not starting (stop it first)` at fatal and exits 1, leaving the marker and sending no alert.

## The watchdog

- A service of its own: the bot's image with `node dist/ops/watchdog-cli.js`, as the image's user, and only the environment it needs (`DISCORD_TOKEN`, `OWNER_ID`, `LOG_LEVEL`, `WATCHDOG_*`). Every thirty seconds it asks the Engine's API (Node's `http` to the socket proxy, `EngineDockerApi`, no client library; ten seconds for a question, the stop's 150 seconds and more for a restart) for the `pine` container of its Compose project (`WATCHDOG_PROJECT`, which compose.yaml names), skipping one-off containers, by the name the list gives (`<project>-pine-<n>`), by which it inspects and restarts it: the proxy takes no id.
- It reads the kind at the start of the health check's last line. `stale` or `missing` (or a line without a kind: the check itself timed out) for `WATCHDOG_UNHEALTHY_MINUTES` (5), counted from when the bot became stuck (a spell of another kind before does not count), while running: it restarts the container (`?t=150`) and DMs the owner with that line. `database`, `gateway`, `slow-start`, `unreadable` for `WATCHDOG_ALERT_MINUTES` (15): it DMs once per unhealthy spell and leaves the bot running, since a restart mends none of them; only `gateway` lasting `WATCHDOG_GATEWAY_RESTART_MINUTES` (5) restarts it after all, in case the client itself is wedged: about seven minutes off Discord in all (Matt, 2026-10-16: members coordinate raids through the bot, so an outage of an hour is not acceptable; a restart during a Discord outage does no harm, and the login backoff bounds a loop). A starting bot is healthy and never restarted. `WATCHDOG_RESTARTS` (3) restarts by Docker's policy within `WATCHDOG_RESTART_WINDOW_MINUTES` (30): it DMs that the bot keeps restarting and leaves it to Docker. Backups are watched only where the project has a `backup` service and its status does not say they are off (then it DMs once that backups are off on this stack, remembered across its restarts): a failed backup, one DM per failure (one older than a day found at its own start is not told again); no good backup for `WATCHDOG_BACKUP_HOURS` (26), a DM at most twice a day. What it told (`/watchdog/watchdog-state.json`) and its alert stamps (`/watchdog/watchdog-alerts.json`) survive its own restarts, in a named volume of its own, `watchdog-state`: `/ops` is root's and mounted read-only, for the backup's result (what it told before plan 8Z stays behind there, at the cost of at most one repeated DM); a state or stamps file that cannot be written is logged. When its asks about the bot fail in a row for `WATCHDOG_ALERT_MINUTES` (15), the proxy gone or refusing, a stuck bot could not be restarted: it DMs the owner once per spell (`docker-away`; a good ask ends the spell, and the next may be told again; the spell is kept with what it told, across its restarts). It looks every `WATCHDOG_INTERVAL_SECONDS` (30). It never restarts any other container, a one-off one or a stopped bot.
- A stuck bot (a blocked event loop, a hung connection) cannot restart itself, a self-kill from inside the bot would need the very event loop that is stuck, and Docker's restart policy acts only on an exit: so something must reach Docker. That is the service `docker-proxy` (`wollomatic/socket-proxy:1`, plan 8Z), the one service that holds the socket, on an internal network of its own and the watchdog's (who also keeps the default network, for its DMs). Its rules, regular expressions of the path that it anchors at both ends, allow `GET` of the list, and `GET` of `<project>-pine-<n>/json` and `POST` of `<project>-pine-<n>/restart`, with or without an API version. They refuse everything else: create, exec, stop, kill, archive, logs, another container's inspect or restart, and so on. `:ro` on the socket does not limit the API: the rules do. Tecnativa's proxy cannot do this (`ALLOW_RESTARTS` needs `POST=1`, which allows `POST /containers/create` with `CONTAINERS=1`). It runs as user 0 with no capabilities, its file system read-only: its own example gives the socket's group, whose id differs per host. Its image carries a health check, `./healthcheck`, over a port of its own on 127.0.0.1 (`SP_ALLOWHEALTHCHECK`), which `./pine status` shows. Checked on an engine on 2026-11-01 (the rules, a restart of a container that ignores SIGTERM, 152 seconds through the proxy, its linux/arm64 image): `2026-11-01-phase-8z-staging.md`. Never mount the socket into the bot or the watchdog.

## Backups

- A `backup` service on the `mysql:8.4` image runs `docker/backup.sh` (the checkout's `docker/` folder is mounted, never the single file: a pulled change is a new file, which a file mount would never show; `./pine update` recreates the service): a POSIX `sh` loop that makes a backup every day at `BACKUP_TIME` (03:30) in `BACKUP_TZ`, or the zone of the settings' `timezone` when that is blank (a zone the image does not know stops the service with a sentence). The image's own `mysqldump` (never MariaDB's client against MySQL 8) dumps `DB_SCHEMA` as root (`--single-transaction --hex-blob --routines --triggers --events`, no `USE` line, so it loads into any schema name), gzipped, as `pine-backup-YYYYMMDD.sql.gz` into `BACKUP_DIR` on the host (one a day; a second run that day replaces it). Only files of that name are ever deleted: those older than `BACKUP_KEEP_DAYS` (90) days, so that exactly that many days are kept; a dump that could not be deleted is logged and is a warning in the status. At the start of the schedule, what a killed run left half-written (`.pine-backup-*.partial`) is removed.
- A blank `BACKUP_DIR` switches backups off (a development or rehearsal stack): the service writes `{"off":true}` as its status and waits, the watchdog watches no backups, `./pine backup` says so and fails, `update` goes on without a backup first, and `restore --replace` over a database with tables refuses unless `--no-backup` (`backup.sh now` exits 3).
- The backup folder must hold a file `.pine-backups`, made once by hand: without it (a share that is not mounted, so an empty local folder) every backup fails with that reason and the watchdog tells the owner. The first stack that writes there puts its project's name into it (`BACKUP_STACK`); another stack is refused that folder, so two stacks never delete each other's dumps. On a share that squashes root, where the backup's owner may not write a marker that root made, the operator makes it as the share's owner with the stack's name in it (`echo pine > <BACKUP_DIR>/.pine-backups`): a marker that already names the stack needs no write. What a killed run left half-written is removed only in a folder so claimed. The folder is mounted with `rslave` propagation, so that a share the host mounts there after Docker started shows inside (Linux only: Docker Desktop ignores it; `rslave` needs the source on a shared or slave mount, which systemd makes every mount by default); on the host, a systemd drop-in for `docker.service` (`/etc/systemd/system/docker.service.d/backups.conf`: `[Unit]` `RequiresMountsFor=<BACKUP_DIR>`) starts Docker only once the share is mounted. If the share was mounted later, `./pine restart backup`. Every file in the folder is written, read and deleted as `BACKUP_UID:BACKUP_GID` (`gosu`; root by default), and a dump can be read by that owner alone (mode 600; it holds members' ids and the keys of the export tool): on a Linux host they are the operator's ids, or `./pine restore` needs `sudo` and says so. For an NFS share (Pittsburgh's Synology), the host mounts it at `BACKUP_DIR` (`/etc/fstab`, `_netdev`), the share's folder belongs to a user of the NAS, and `BACKUP_UID` / `BACKUP_GID` are that user's ids, so that a share that squashes root still takes the files; the guide of plan 8L-2 covers the mount.
- Every dump is verified before it takes its name: a second `mysqld` (no binary log, no double writes, no flush per commit) with a temporary data directory in the `backup-scratch` volume loads it (`--commands=OFF`, as `./pine restore` does: what a dump asks of the client, such as `\!` to run a program, is not done, even in a `/*!…*/` comment); its tables must equal the live ones, `kysely_migration` must have rows, and `Guild`, `Region`, `Gym`, `User` must have rows where the live ones do (a count the live database does not give is a failure). Then the scratch server is thrown away; what a stopped run left there goes at the next start. The volume needs room for the database about twice over, on the host's Docker disk. A failed run keeps the day's earlier dump.
- One backup at a time: a lock holding the pid of its run (a lock whose run is gone is taken over). A scheduled run that finds one running records a failure ("a backup was still running"); a run asked for now (`./pine backup`, before a restore or an update) only says so and fails.
- The result goes to the log and to `/ops/backup-status.json` in the `ops` volume (`readBackupStatus`, `src/ops/backup-status.ts`, is the watchdog's reader; `backup-status.sh.test.ts` runs the script's own `write_status`, sourced with `BACKUP_SH_LIBRARY`), with a line for `./pine status`. `./pine backup` runs one now through the same code (`backup.sh now`). `restore --replace` (of a database with tables) and `update` make one before they change the database (`backup.sh now before-restore` / `before-update`: a file of its own, `pine-backup-YYYYMMDD-HHMMSS-<tag>.sql.gz`, so that it never replaces the day's backup, which may be the very dump being restored), and stop when it fails.

## Restore

- `./pine restore <dump.sql | dump.sql.gz> [--replace [--no-backup]] [--start | --no-start]`, in this order, nothing stopped until the dump is known good: the dump must be whole (`gzip -t`) and end with mysqldump's `-- Dump completed` line; `mysql` is started alone; `restore-cli.js check` refuses a database that has tables without `--replace` (with it, exit 3: a verified backup of it is made first, unless `--no-backup`). Then `pine`, `watchdog` and `backup` are stopped; `restore-cli.js prepare` drops the database and creates it anew (utf8mb4); the dump is streamed from the file into the `mysql` container's own client as root (`docker compose exec -T`, never copied; gzip's status kept, as sh has no pipefail); `restore-cli.js finish` renames lower-cased tables to the bot's names in one `RENAME TABLE` (the foreign keys follow; `canonicalRenames`, `src/db/table-names.ts`) and prints what was loaded: legacy or Pine, the tables, the rows of the main ones. A legacy database without its last migration is reported as the migrator's refusal and refused (`finish` exits 4), as is an empty or unknown one: the script then says the bot, its watchdog and the backups stay stopped and another dump is needed, never "./pine up". Then the stack starts (on a terminal, or with `--start`) and the migrator takes the database over or migrates it.
- `restoreStep` (`src/ops/restore.ts`) is the CLI's logic, tested against MySQL with its exit codes. `PINE_TABLES` lists every table the bot knows (the legacy ones from the generated baseline); a migration that adds a table adds it there, or `restore.db.test.ts` fails.
- `./pine migrate` runs the migrations in a one-off container without starting the bot: no Discord. It is how a restored copy is checked without logging in.
