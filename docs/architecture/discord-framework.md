# Commands, controls and answers

How the bot talks to Discord apart from parties: slash commands and their router, subcommand groups, deferral and late answers, component controls and their throttles, how a press answers (in place, apart, as a copy), where an interaction came from, and the components-v2 messages every answer is made of. Read before adding or changing a command, a control or the way something answers.

## Commands

- Every slash command is a `CommandModule` listed in `src/commands/index.ts`; the router and the deploy script both read that list. A command that lost its subcommands (`/settings`, plan 8S-5) names them in `SimpleCommand.formerSubcommands`: if Discord delivers a use of one from a client that has not seen the new definition yet (its client may refuse an outdated command before sending it, review A6), the command runs as it is now, its options unread, rather than being refused as unknown. A command with another name is listed under both: `alsoAs(command, name)` (`src/discord/command.ts`; `/hmm` of `/interested`, `/coming` of `/join`) gives the same guards, handlers, throttle and help under another name, and a short form (`/little`, `/great`, `/ultra`, `/master`: `/rank` in that league) is a command of its own with `formOf`. The uses of a form count as the command's (the router's throttle key), "You can use /x again" names the name typed, and `/help` lists a form beside the command's name on its line and explains it as the command's.
- A command with subcommands is built with `commandGroup({ data, help, guards, groups, parts })` (`src/discord/command-group.ts`): each part carries its own subcommand builder, `guards`, `execute` and `autocomplete`. The router refuses to start when the definition and the handlers differ. Command guards run before the subcommand's.
- Commands are offered in servers only, and for server installs only, unless the definition sets its own `contexts` (`/help` adds the bot DM). A command that depends on a setting has `enabled(config)`; `enabledCommands()` filters the list for the router, `/help` and the deploy script alike.
- A message command (plan 8S-2: an entry of Discord's Apps menu on a message, a right-click or a long press, such as "Report to moderators") is a `MessageCommand` (`src/discord/command.ts`: `target: 'message'`, its `data` a `ContextMenuCommandBuilder` of type Message, `help` with a `description` of its own, `guards`, `throttle`, `defer: 'ephemeral'` or none, and `run(interaction, ctx)`), listed in `messageCommands` beside `commands` in `src/commands/index.ts` (Discord allows five, `MAX_MESSAGE_COMMANDS`). Discord sends the message it was used on with the interaction, its text included, without any intent (`interaction.targetMessage`). The router takes both lists in one (`new InteractionRouter(ctx, [...commands, ...messageCommands], …)`; a name twice among the message commands is refused, and their names are apart from the slash commands'), runs guards, throttle (counted under the name the menu shows: "You can use Report to moderators again in …"), the private acknowledgement and `run`; guards take it (`LocatedInteraction`), as `answer` and `answerApart` do. `enabledMessageCommands(list, config)` filters it as `enabledCommands` does; `buildCommandPayload(commands, messageCommands)` registers them after the slash commands, offered in servers and installed to servers only. `ctx.messageCommands` is what `/help` lists: under its name in its group (`**Report to moderators** (Apps menu)`, after the slash commands), its page by that name however typed (`/help command:report to moderators`, offered while typed), its usage the way to the menu (`messageCommandUsage`). Tests use `fakeMessageCommand({ targetMessage })` (`test/support/fake-interactions.ts`; `FAKE_BOT_ID` is the bot's own user, `interaction.client.user.id`). The second is "Read screenshot" (plan 7M, `screenshots.md`): deferred privately, enabled by `ocr.enabled`, and without a router throttle, since each picture of the message is a use the screenshot trigger counts in the member's window of mentions.
- A part of a `commandGroup` may have `enabled(config)` (`SubcommandPart.enabled`): `enabledCommands()` then narrows the command to the subcommands its settings offer, for the router, `/help` and the deploy script alike (`/admin self-roles` exists only where `features.roles` is on).
- For a command with `default_member_permissions` the router runs the command-level guards also for an autocomplete interaction and answers an empty list when one refuses; such a guard must cope with an autocomplete interaction and read no options. Ordinary commands' autocomplete runs no guards. `/operator` (plan 19B-1), offered in a DM with the bot too, where Discord ignores the permissions, has them for this: its guard (the shared-data tier, `servers.md`, "The operators") keeps a non-operator's autocomplete empty there.
- Autocomplete is counted by no throttle and runs on the thread that holds the gateway, so the router answers it with no choices, before any guard or handler, when any text option of the interaction (the one being typed or one filled in before, under a subcommand too) is longer than `MAX_OPTION_TEXT` (1,500 characters, `src/discord/command.ts`; plan 8Z-2, the audit's M5): Discord's client holds an option to its `max_length`, a client of somebody's own need not. It is the most any option declares (`MAX_PLACE_TEXT`, a place's maps link); `src/commands/option-lengths.test.ts` holds every text option of a command that offers choices to a declared `max_length` of at most it (fix round F-A7: one declared none, whose limit is Discord's 6,000, fails too; an option that takes a short word offered by autocomplete, a group's letter, declares `MAX_CHOICE_TEXT`, 100, the longest value a choice may have), but an option with fixed `choices` (a tier, a league, `/counters`' settings), which takes no free text and declares no `max_length`: the test refuses one that does (fix round F-A8: whether Discord takes both was not confirmed, and a command it refused would fail the whole deploy). What reads typed text must still be linear in it (`unlistedMega` reads a name with its white space collapsed), and a table of words is read through `Object.hasOwn`, never a plain index (`constructor` is no tier, entity or kind).
- `/admin` is a `commandGroup` whose parts are listed in `src/commands/admin/index.ts`: a new subcommand is a file there, appended to that list. What every server shares is `/operator`'s (`src/commands/operator/index.ts`, plan 19B-1): a subcommand that changes such data goes there, on the shared-data tier, and tells the owner (`tellOwnerOfSharedChange`). `/raid` reads what a member picked or typed through `src/commands/raids/raid-input.ts` (`reportedBoss`, `reportedGym`, `reportedTime`); a question to the member (a menu, a confirmation) keeps its values in a `PendingRequests` store under a token that is the id of the controls' custom id. A token is the member's and the server's it was asked in (plan 19B-4): `put(asker, …)`, `take(token, asker)` and `peek(token, asker)` take the interaction (an `Asker`: `user.id` and `guildId`, null in a DM; the screenshot trigger's question its message's author, `authorOf`), and a press from another server, or from a DM for a server's question and the other way round, is `expired` whoever presses it, never `not-yours` (which would tell that it exists), the question staying for its own server. The kept options of `/counters` (`KeptCounterOptions.keep(value, serverId)`, read with `of(token, { guildId })`) are of the answer's server (`NOT_KEPT` from another), and Change options… keeps nothing per press: its dialog is `counters:<answer's token>:dialog:<opener id>`, whose Submit by anybody but the opener is `NOT_YOURS`. The custom-id kind `raid` belongs to `/raid`'s own controls.
- A refusal that needs a control of its own (the Appeal of a member blocked from making meetups, `meetup-safety.md`) is a `UserError` with `answer` (a `V2Message`): the router shows that message privately (`answerApart`) where the interaction is not answered yet or was deferred privately, and the text otherwise.
- A command's `throttle` may be a function of the interaction (`/meet`: 3 per 180 seconds in a timed party); a use that a guard refused does not count, so what can be known before the work (a bad name, no region, an unreadable time) is refused by a guard that reads the options (`/meetup`, `/meet`), and `execute` keeps its own checks.

## The router and deferral

- The router's order is guards, checks (plan 8S-3, below), throttle, deferral, `execute`; before all of it, in rehearsal mode (`ctx.rehearsal`), a member who is neither on its allowlist nor staff gets `REHEARSAL_REFUSAL` and nothing else (`operations.md`). A handler that needs more than three seconds declares `defer: 'ephemeral' | 'public'` and then uses `editReply`/`followUp`; it never calls `deferReply` itself. A command whose work is short (a read or a write of the member's own rows) declares `defer: 'late'` instead: it runs at once and answers through `answer(interaction, payload)` (`src/discord/late-reply.ts`), never `editReply`, in everything it runs; `answer` sends the first answer directly (for the member alone) when nothing was acknowledged and edits otherwise, and the router acknowledges such a command only when it has not answered `LATE_DEFER_MS` after the interaction was made (one request to Discord is a quarter of a second, so deferring first doubled the wait). A test reads what such a command said with `answered(fake)` (`test/support/fake-interactions.ts`). `defer` may be a function of the interaction for a command that opens a form for some uses and works for long in others (`/counters`; `/max`, plan 8X-3, which asks in a dialog about a new battle that ends within five minutes, and reads what its guard read, kept by the interaction); a command that opens a dialog declares none (the dialog is its first answer). A component handler that sends to Discord before it answers acknowledges itself first (`deferReply` in the form of `/report` and of Report to moderators, `src/commands/parties/report.ts` and `report-message.ts`, and `deferSubmit` in the Submit of every one-shot dialog, below). `throttle: { uses, perSeconds }` limits a member per command path; a use that a guard refused does not count.
- Plan 8Z-2 (fix round F-A5): the attendance commands (`/join`, `/interested`, `/here`, their other names, `/remote`, `/local`, `/not-here`, `/leave`, `/done`), `/group join`, `new` and `label`, `/meet`, `/cancel-meet` and `/end` declare `defer: 'late'`: the attendance service asks Discord how a newcomer stands to the party's forum before the write, and in a meetup `requireMeetupChanger` reads the maker's block, either of which may eat the three seconds (`runLate` counts from the interaction's creation, so a slow guard is covered). Their shared answers (`answerOutcome`, `replyTimed`, `replyRaidChange`, the max battle's `/end`) go through `answer`, which replies as before where nothing was acknowledged, so their other callers (`/hatch`, `/boss`, `/location`, `/name`, "Set time…") are unchanged; none of them opens a dialog.
- Plan 8S-3: between the guards and the throttle the router asks `checks`, the window a form's submit counts in, of a command (`CommandHandler.checks`, a `ControlThrottle`: `as` its command, else the command's own), a message command and a control (`ComponentHandler.checks(interaction, id)`, the limit `throttle` gives the form, counted where the form is): while that window is full the use is refused (the window's words: "You can use /report again in …", "That was a lot of clicks…"), and either way nothing is counted (`Throttles.wait`), so nobody types into a form only to be refused. `/report` and Report to moderators check `/report`'s window (`REPORT_WINDOW`), Ask the moderators and Appeal their form's (`APPEAL_THROTTLE`). A handler's own check before its form is a quick read (whether the member reported it already: `moderation.md`); when it fails the form opens as before, and the submit's checks stay (two forms open at once, a restart between).
- A `LockOverdueError` (a change that waited too long behind one of `PartyStore`'s locks, `parties-and-posts.md`) is answered `STILL_BUSY` ("I am still busy with an earlier change to this. Try again in a moment."), not logged (the lock logs its holder once), and its use is given back as for any other error that is not a `UserError` (2026-11-07). The refusal comes up to a minute after the press: it reaches the member where the interaction was acknowledged by then (a deferred command; a control press with the router's late deferral, `LATE_DEFER_MS`, of branch `help-and-three`).
- Plan 8S-3: every use the router counted (a command's, a message command's, a control's) is given back when its work throws anything but a `UserError` (`Throttles.giveBack`; at most `uses` a window, so a use that keeps failing is held to twice its limit), and when a `UserError` says it is none of the member's doing (`givesBack`: the bot may not make posts in the forum, the moderators could not be asked: a meetup held for them, an ask about a place, an appeal or a report that was `not-sent`). A use goes back only to the window it was counted in (`countedAt`, when it was counted: a window opened since, after the use's own closed, gets nothing). A form or a question whose command counted the use names that command's window and when the use was counted with `ComponentHandler.carriesOn` (`/meetup`'s form: `MEETUP_THROTTLE` as `meetup`; `/raid`'s gym menu and buttons: `RAID_THROTTLE` as `raid`; `/location`'s dialog, whose Submit refused for no post in the other forum gives back the Submit and the use that opened it, plans 8S-4 and 8Q, the time carried in the dialog's custom id: `CHANGE_THROTTLE` as `location`; a move that landed and was answered before a later step failed is logged and keeps both counted; undefined for a form it no longer knows), and its failure gives that use back. The time is the router's own (`whenCounted(interaction)`, `src/discord/router.ts`: when the router counted this use, by `RouterOptions.now`), never a clock the handler reads again later (`/raid` with a screenshot reads it first, which may take minutes). A refusal a handler has said in its own answer (`UserError` with `said: true`: `/raid`'s "no post" in its answer, the screenshot's feedback button kept) is answered no more by the router; with `givesBack` its use still goes back. A refusal is the member's and stays counted. One exception by Matt's ruling (plan 8R-6): "Already reported" does not count, so `/research report` (with its "Same task at more stops…" and its dialog "Replace field research?"), `/rocket report` (with its dialog "Replace a hideout?") and the map's research and Rocket routes give back a use that reported at no stop, after their answer (`said` and `givesBack`; on the map `givenBackOnTheMap`); see `stop-reports.md`. The live map gives back what it counted the same way where it shares a window (`givenBackOnTheMap(deps, command, userId, throttle, countedAt)`: meetups, trains, raids, and since 8S-4 the changes of a raid, in the window of their command). The trade-off (review of 8S-3): a use is given back whenever the work throws, also when its effect had landed before (the party made, then its answer refused: an `editReply` that failed, Unknown interaction); accepted, since at most `uses` go back a window, so such a member gets at most twice the limit, and a handler cannot mark a point after which nothing goes back.

## Controls and how a press answers

- Controls are `ComponentHandler`s listed in `src/components/index.ts`, one per custom-id kind, with a function per control type (`button`, `select`, `modal`). A command's guards do not cover its controls: give the handler its own `guards`. Its `throttle` may be a function of the interaction and the custom id (asked after the guards; undefined lets a control through uncounted): `/counters` counts a submitted dialog in the command's window and the button that opens it in a `MEMBER_READ_THROTTLE` window of its own. A limit with `as` (`ControlThrottle`) counts in the window of that command, as the router counts the command's uses (the dialog of `/counters` runs the command's work against Pokebattler: command and submits share its three a minute, "You can use /counters again in …"); without it a control counts in its kind's own window (`controlThrottleKey(kind)`, `component:<kind>`), as `/rank`'s and `/help`'s do. The bot's one `Throttles` is `ctx.throttles` (plan 8Z: `submitSplit` counts a split in `/train`'s window with it; `RouterOptions.throttles` overrides it in a test), which the router counts in and the web server shares, whose presses of a party's buttons count in the window of the post's controls (plan 8M-3). What a control refuses belongs in a guard of its handler, which runs before the throttle, so that a refusal does not count (`requireDialogPlan` of `/counters`' dialog).
- A control whose answer waits for a write declares `defer` (`ComponentHandler.defer(interaction, id, ctx)`, 2026-11-07): `'late'` has the router acknowledge the press for the member alone (`deferReply`, "thinking…") when it has not answered `LATE_DEFER_MS` after it was made, as a command's late deferral (`deferLate`, the router's `runLate`); undefined for a press that answers otherwise, above all one that opens a dialog. A post's buttons declare it for every press that writes the party (Interested, Join, Here unless they ask which group first, Done, Leave, +1, −1, Remote, a group's letter, the completion question's answers): a quick write is answered as before (`ClickAnswers`, a private reply), a slow one in the place of the acknowledgement (`editReply`; `lateSettled(interaction)` of `late-reply.ts` stops or awaits it first), so Discord never gives up on the press ("This interaction failed"). A later click of a burst that was acknowledged so is answered by itself and ends the burst, so that no older answer gathered in it is shown after it.
- A dialog (a modal; `showModal`, the first answer: nothing is deferred before it) holds up to five labels, rows of a text input and text displays. Checked on the test server (2026-10-18, plan 8T-H): a dialog of one text display alone opens and submits (the split's one-group dialog), and a label may hold a radio group (`ComponentType.RadioGroup`, 2 to 10 choices of a label, value and description of 100 each), read with `fields.getRadioGroup(id, true)`; a required one cannot be submitted empty (Discord refuses Submit), so nothing is preselected where a pick must be deliberate. A label may also hold one tick box (`ComponentType.Checkbox`: a `custom_id` and `default` only, its words the label's and its description's; `fields.getCheckbox`, plan 8R-4: Costumes and Remove of `/want`'s dialog), not yet checked on Discord (8R-4's staging). Labels and descriptions of choices are assumed to show no markdown, as those of select menus do (not yet checked on Discord: 8T staging step 28 checks it): they carry the members' text as it is, not `plain()`.
- A question asked once ("Remove all your wants?", "Close this raid?", the split of a train; plans 8T-H, 8Q, design `2026-10-18-one-shot-dialogs-design.md`) is a dialog, not a private reply with buttons: it opens over the channel at once and closes when answered. They are Remove all of the wants and gym targets (`notifications-and-dms.md`), staff's `/delete` and Close…, Refuse place…, Block maker… of a report's post (`removalDialog`, `moderation.md`), deleting a gym and `/region remove` (`gyms-and-regions.md`), `/location` to another region (`parties-and-posts.md`), the split of a train (`trains.md`), "Turn your history off" of `/settings` (plan 8S-5, `members-and-roles.md`: asked only where turning it off takes something away; its Submit `settings:history:forget` is acknowledged on the panel with `deferUpdate` and redraws the panel in place, as the Submit of Manage… of a line of `/wants` shows the list again in place, `notifications-and-dms.md`, rather than answering privately apart) and `/max`'s question about a battle that ends soon (plan 8X-3, `parties-and-posts.md`: no read from the database, the slow-read rule's clock checked before it opens; its Submit `max:<token>:report`, a pending-request token, carries on the use `/max` counted) and an operator's "Remove a member’s data" under the look of `/operator forget` (plan 8G, `members-and-roles.md`: a text alone, "This cannot be undone. Submit removes it."; its Submit `forget:<token>:remove`, a pending-request token of the operator who asked, acknowledged on the look with `deferUpdate` and answered in its place, v2.0.2); the panels used again and again, the import previews and the like stay private replies. The pieces are `src/discord/dialog.ts`: `dialog({ customId, title, text?, choice?, field? })` (the title says the act, cut to 45 characters; the text is the question, ending with what Submit does when there is no choice, `Submit removes them.`, and may be left out of a dialog that is its choice alone; a choice between ways is a required radio group with nothing picked, so that Submit never does the harsher one by default, read at Submit with `pickedOf` (undefined for a Submit without that group, a dialog of an older shape or a forged one: the handler then answers stale); when only one way is possible there is no choice and the text says why). Plan 8X-1B: a choice may name the value `picked` to start with (Discord's `default`; the fakes refuse two, as Discord would), which goes first in its list where the order allows: Android picks a radio group's first choice by itself whatever is marked (Matt's check, 2026-10-20), an iPhone only what is marked, so a choice that must not be made by accident is never first; `menu: true` makes it a string select of up to 25 for a longer list (Meet…, `getStringSelectValues`), whose default is marked only (it keeps its order). Discord's client keeps what was submitted in a dialog per custom id and shows that again in place of the value marked (the staging of 8X: Meet… showed the time submitted before, not the group's), so a dialog that marks a value to start with (Meet…, the which-group dialog, Group…; since plan 8R-4 `/want`'s Pokémon, tier and Team GO Rocket dialogs, whose Submits refuse an id without it, as none was drawn without one), and a radio dialog that starts with nothing picked where an earlier pick could come back after a refused Submit (the split's picker and one-group dialog, `removalDialog` of `/delete` and a report's Close…, Refuse place…, Block maker…, `/region remove`; 2026-10-22, from the 8X staging's finding) ends its custom id in a per-open token, `openToken(now)` (`~` and the moment it opened in base 36, about ten characters: count them in the 100), which its Submit leaves out with `withoutOpenToken(args)` (plan 8X-F; a dialog drawn before without it submits as before); `field` is one optional line of text (`TextInputStyle.Short`, `required: false`), its `value` what it holds to start with (plan 8S-5: the Pokebattler id of `/settings`, changed rather than typed again; such a dialog ends in `openToken` too). Plan 8X-G: `choices` asks several, each under its label after `choice` (Manage… of a train: "The route" as a radio group, the mode and the kind as menus; Discord takes five components in a dialog, the text included), a menu's options with their `emoji` (a radio group shows none), read at Submit with `pickedOf` (a radio group) and `selectedOf` (a menu: the option chosen when it is one of the values, else undefined). Plan 8M-21: `asks` lists choices and lines of text in their order after the text (Manage… of a raid and of a meetup, which ask lines first); a menu may stay empty (`optional: { placeholder }`, `required: false`, `min_values: 0`) and a label may have a `description`; a line of text may be a paragraph (`paragraph`) or `required`. A command whose throttle varies counts in `variedThrottleKey(name, limit)`; a control that counts in that window (`as`, Meet…'s dialog in `/meet`'s; "Same task at more stops…" in `/research report`'s, plan 8R-1, whose limit is of the settings: a control's `throttle` function gets `(interaction, id, ctx)`) is refused in the command's words, the name before the line break ("You can use /meet again in …"). Discord's Cancel replaces the Keep and Cancel buttons: it closes the dialog and nothing is said. **The slow-read rule:** what a dialog needs from the database (a count, a report, a gym's references, the member's privacy) is read through `readInTime(log, interaction, work)`, within `DIALOG_READ_MS` (2 seconds, of Discord's 3) of when the interaction was made (its `createdTimestamp`, as the late deferral counts): past it no dialog opens and the member is told privately `SLOW_READ` ("That took me too long to look up: try again in a moment."), a `UserError` that gives the use back; a refusal of the read itself passes on (also one thrown at once, which leaves no timer), a read that comes back past the budget by the clock is refused too (also before its timer ran, on a busy event loop), and a read that fails after it was given up is logged. A command that opens a dialog declares no `defer`, and a control does not defer before it. Where the read decides whether a dialog opens at all, and the use goes on without one (`/research report`'s "Same task at more stops…", plan 8R-5, review F1: `readOrDefer` in `research.ts`), the read is raced against the same budget: back in time, as above; past it, the press is deferred privately at once, and when the read comes back the dialog it would need is refused with `SLOW_READ` in the deferred reply (the use given back), while without one the use goes on. The dialog carries what it needs in its custom id (the party, the gym, the region, the report); a pending-request token only where a value does not fit or must not be shown. Its Submit is a `modal` of the handler of the same kind, with the same guards and throttle as the press it replaces (opening counts as the question did); it is acknowledged privately at once (`deferSubmit`), decides everything again, and answers privately (`editReply`, `answerApart`, or a `UserError` the router says). **Channels in a dialog are named, not mentioned:** `channelInDialog(name)` (`#oakland`; `a deleted channel` for one the bot cannot find), since whether Discord shows `<#id>` inside a dialog is not checked yet (8Q staging); the answers after Submit keep their mentions. Tests read a dialog with `test/support/dialogs.ts`.
- A press on the controls of an answer (plan 8B-2) is answered through `pressAnswer` / `deferPress` / `answerPress` (`src/discord/late-reply.ts`): on a public answer (`/rank`, `/counters` in a post) the member who asked (`message.interactionMetadata.user`, never the deprecated `interaction`) changes the answer for everybody (`update`), anybody else gets a private copy with the change; a press on a private answer always changes it; `onlyPrivate` (a Pokébox) gives even the asker a copy. Work that takes time acknowledges first as it will answer (`deferUpdate` or a private `deferReply`; a form submitted from no message has nothing to update and is deferred as a copy). A public answer in a party's post whose party has ended is never edited: the press answers privately.
- **A party named by a custom id is a party of the interaction's server or none** (plan 19B-4; spec, "The rule"): every control, dialog and guard that reads a party by the id in its custom id reads it through `partyOfServer(interaction, ctx, partyId)` (`src/discord/guards.ts`: the party only where its server, as its `Guild` row names it in memory, `PartyService.serverOf` over every row read at the start, is the interaction's; undefined in a DM; synchronous, so a guard and a press before a dialog ask it), and answers undefined in the words it has for a party that has ended (`partyOver()`, `STALE_COMPONENT` where that is what it says of one gone), never in other words that would tell that it exists: the post's buttons (a press that writes attendance answers `{ kind: 'gone' }` before the service is asked; `answerClick` names no kind of another server's party), Set time…, Screenshot feedback, Manage…, Move…, Route, Split…, Group…, Meet… and their dialogs, `meet`, `tmanage`, `mmanage` and `rmanage` with the guards that read their times (`requireTimesChange`), `maxpin`, and the Submits of `pclose`, `report:<party>:party`, `location` and `info` (the last two also only the party of the post they are submitted in). Tests press from `OTHER_GUILD_ID`, a server with a row of its own, and from one without a row (`src/components/party-servers.test.ts`).
- A control that answers in the place of the message it is on, where that message may be from before it was v2, uses `showInPlace(press, message, oldLine?)` and `sayInPlace(press, text, accent)` (`src/discord/late-reply.ts`; `onV2Message`): on a v2 message an `update` (or an edit after `deferUpdate`) with its files replacing the old ones (`attachments: []`); on a classic one `sayInPlace` answers plain text, and `showInPlace` closes it with `oldLine` (`ANSWERED_BELOW` unless given) and sends the v2 message as a private follow-up, since whether Discord takes a v2 interaction update of a classic message is not known and is not tried; a form a command opened is answered privately. Controls backed by `PendingRequests` (the questions of `/gym` and `/region`) meet a message from before a restart as expired, so these classic paths are a safety net for them; in practice only stateless controls (the `/iam` menus) reach them. An answer in a private message of its own (a command, or a press acknowledged with `deferReply`: `answeredApart`, told by discord.js setting `ephemeral` for a reply or `deferReply` and not for `update` or `deferUpdate`) goes through `answerApart(interaction, message)`; `showInPlace` throws there, and `sayInPlace` answers apart. In tests the fake controls take `v2Message: true` for a press on a v2 message whose rows the test does not give (`gymCommandsWith` and `regionCommandsWith` press so by default; `v2Message: false` is a message from before), and refuse as Discord would: a v2 `update` (or edit after `deferUpdate`) of a classic message ("a classic-to-v2 update is not tried"), a v2 message made classic, and a file component, thumbnail or gallery picture naming a file the message does not carry (a reply and a follow-up carry only their own `files`; an edit that sends `files` without `attachments` keeps none of the old ones, as discord.js sends it). `V2Message.files` are `MessageFile`s: a local path, or text made with its name (`{ attachment: Buffer, name }`).

- **Share** (plan 8H-5, the first: `/stats regions`, `history.md`; plan 8H-6's `/stats boards` and `/stats me` follow it, through one `shareMessage` of `stats.ts`): a button under a private answer that posts the same view in the channel for everybody. The convention:
  - its own custom-id action with what the view is made of as arguments (`stats:regions:share:<period>`); only the answer's member can press it, the answer being private;
  - the view is computed again at the press, as it may be shown in that channel, never what only the sharer may see: what a place's forum keeps from somebody who sees the channel stays out (`PartyGateway.shareKeeps`, Matt's ruling R-A, `history.md`);
  - where the bot may not post there it is refused in words before anything is sent (`PartyGateway.mayShare`: View Channel and Send Messages, or Send Messages in Threads in a post; no Embed Links, which components v2 does not need; never in an ended post, archived and locked, which is not opened for it), after a refusal (`isMissingPermission`, or `isArchivedThread` for a post that ended meanwhile, 50083) or a channel that is gone, and where the cache lacks the channel, so that who sees it cannot be said; each `givesBack`;
  - where the sharer may not write there themselves it is refused first, in words (plan 8Z-2, the audit's L-D5: the post is the bot's in their name, so a read-only channel or a member a role keeps from writing got a message through it): `interaction.memberPermissions`, what Discord says the member may do in the channel of the press, must hold Send Messages, or Send Messages in Threads in a post or thread (`sharerMayWrite`, `ShareWords.notYours`: "You may not send messages in this channel, so I cannot share the list here for you."); `givesBack`;
  - a press of an answer's other controls that reads (another period) races its read against what is left of `LATE_DEFER_MS` and defers the press as it will answer when the read is late (`readOrDeferPress`, `inTime` of `src/discord/late-reply.ts`, which `/research report`'s read before its dialog shares);
  - the press is acknowledged with `deferUpdate` before the send (the private answer stays as it is) and answered with a private follow-up;
  - the post is the bot's, its sharer named in its small print (`-# Shared by` and `memberByName`), or once in its title where the view is the sharer's own (`/stats me`'s "History of **name**", no small print), mentions off, nothing on it to press;
  - its refusals in the words of what it shares ("… the list …", "… the board …", "… your numbers …": `ShareWords`);
  - a throttle of its own, counted apart from the answer's other controls (a throttle function by action); the Shares of one command's answers may share it (`/stats`' three Shares count in one `SHARE_THROTTLE` window, three posts in ten minutes);
  - what only the sharer may see stays out: a board leaves out the viewer's own place, a member's card every anonymous record (plan 8H-6).
- **A labelled button that opens a dialog ends in `…`** (plan 8X-G; Matt, 2026-10-22: a post control that needs more input opens a dialog, never a private reply with controls): Group…, Meet…, Move…, Manage…, Split…, Set time…, Something is wrong…, Appeal…, Ask the moderators…, Delete… (the moderators' notice of a pin battle), Open the form again…, Change options…, Close…, Refuse place…, Block maker… and the others; a button that only shows something has none (Route, Screenshot feedback, Go to post). Text that names such a button names it with its `…` (`"Set time…" gives them.`, `press "Appeal…".`); an icon-only button (Meet…'s ⏰) is named by its icon.

## Where an interaction came from

- Where an interaction came from is read only through `channelContext(interaction)` (`src/discord/channel-context.ts`): a thread or forum post is judged by the channel it is in (`baseChannelId`), and a DM is `!interaction.inGuild()`, never the channel cache. `regionChannelOf(interaction, ctx)` gives the region channel or undefined. Both also take an autocomplete interaction (`LocatedInteraction`).

## Components-v2 messages

- Every message that is more than plain text is a components-v2 message (Matt, 2026-10-15): no code builds an embed (`APIEmbed`, `EmbedBuilder`; plan 8B-4 converted the last). Only the classic text spawn report for a channel without Embed Links stays plain until staging says whether v2 needs that permission; `ClassicMessage.embeds` and the fake gateway's embed checks remain for the messages made before (a conversion clears them).
- Every new message of the bot that is not plain text is a components-v2 message, never an embed (Matt, 2026-10-15), ephemeral answers included: one `container` of `textDisplay`s and rows from `src/render/v2.ts`, sent and edited through `discordPayload({ v2: true, components })`, and every later edit of it v2 as well (a v2 message cannot become classic again: "Importing…", the outcome, Cancel and "expired" of `/gym import` are v2). A file sent with such a message is shown by `fileComponent(name)` (`attachment://<name>`), an edit that drops it passes `attachments: []`. What a batch changed is announced in one summary (`gymListSummary`, `src/render/gym-summary.ts`). A message of sentences is `textMessage(accent, texts, more)`.

## Downloads

- An attachment is downloaded only through `AttachmentGateway.download(url, { maxBytes, timeoutMs })` (`src/services/attachment-gateway.ts`): https, Discord's attachment hosts only, no redirect, a hard byte limit, the address never logged. Tests use the fake in `test/support/attachments.ts`.
