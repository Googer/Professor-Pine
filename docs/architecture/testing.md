# Testing

Tests are colocated, use real MySQL and real loggers, never the network, and run against strict fakes of Discord. This file lists the helpers and fakes of `test/support/` by area. Read before writing or changing tests.

## The database and the network

- Tests are colocated: `*.test.ts` (unit, no Docker) and `*.db.test.ts` (needs Docker). Test against real MySQL and real pino loggers (`test/support/`) rather than mocks. A run of the database suite starts one MySQL container (`test/support/mysql-global-setup.ts`); `startDatabase()` (`test/support/mysql.ts`) gives each caller a database and a user of its own in it and drops both at `stop()`. The user also has `PROCESS`, to see the server's transactions: a test that has a statement wait for a lock asserts the wait (`information_schema.innodb_trx`, joined to `processlist` on its own user, since the server is shared): `lockWaits(db, holder)` (`test/support/lock-waits.ts`) asks until a transaction other than the holder's (`connectionId(trx)`) waits, every 150 ms (InnoDB fills the table anew only once it has not been read for 0.1 seconds), with a deadline of ten seconds.
- A database test that a statement draws no warning of MySQL (a deprecated syntax, `DEPRECATED_SYNTAX` 1287) runs it through `lastWarnings(db, work)` (`test/support/mysql-warnings.ts`): `work` in a transaction of its own on one connection, then `show warnings`, which follows its last statement rather than the commit's (plan 8W-3).
- Tests never use the network. Game data in tests comes from the fixtures built by `scripts/game-data/make-fixtures.ts` (`catalogueFixture()`, `gameDataFixture()`); raid bosses come from `test/support/raid-bosses.ts` (`readRaidBossFeed()`, `raidBossesFixture()`, and `MemoryRaidBossStore` for the service, a `MemoryBossStore` of the raid family). Leek Duck's raid rotations (plan 8B-L) are recorded in `test/fixtures/raid-manifest/`: the manifest of 2026-10-27 and the pages of five rotations (`ROTATION_SLUGS`: the Palkia week, Halloween Part I, the Giratina week, the Chandelure Super Mega Raid Day, the shadow Landorus rotation), with ScrapedDuck's `raids.json` of the same moment, read through `test/support/raid-manifest.ts` (`readRaidManifestFixture()`, `readRaidManifestText()`, `readRotationFixture(slug)`, `readScrapedDuckRaidsText()`); `raid-boss-manifest.test.ts` serves them by address from a fake `fetch` (an address it lacks answers 404). Max bosses (plan 8X-2): the recorded Pokebattler feed `readPokebattlerFeed()`, a feed of its shape `pokebattlerFeed(tiers)`, `MAX_FEED_READ_AT`, `MAX_ZONE` and `at(local)` (`test/support/max-bosses.ts`), the recorded max events `readMaxEventFeed()` (`test/support/max-events.ts`), and `maxBossServiceWith()` (`test/support/max-boss-service.ts`: a real `MaxBossService` over `MemoryMaxBossStore`, nothing stored yet, `restarted()` for a restart); `bossCommandsWith({ max: true })` turns max battles on for `/admin boss`, its override ids counted with the raid bosses' as in the one table (`ids`). Pokebattler in tests is `FakePokebattler` (`test/support/pokebattler.ts`: `asked`, `answer`, `known`, `failing`; `answerSimulating(movesets)` an answer that simulates those boss movesets in that order, plan 8X-H; for max battle teams, plan 8X-6, `maxAsked` and `maxAnswer`, by default the recorded Uxie team of two attackers and a charger, whatever the role; the Azelf teams of Pokebattler's four roles, plan 8X-I, are `azelf-d5-…`); the recorded max team answers of 2026-10-21 are `recordedMaxTeam(name)` (the JSON as Pokebattler gave it, `test/fixtures/pokebattler-max-teams.json`) and `recordedTeam(name)` (read by `readMaxTeam`).
- Gyms and regions in tests are the invented ones of `test/support/gyms.ts` (never production rows); `createTestContext()` provides `ctx.gyms`, `ctx.pokemon` and `ctx.maps` from `test/support/providers.ts`.

## How the suites run

- The projects of `vitest.config.ts`: `unit`, `isolated`, `shell` (`*.sh.test.ts`, which start Git Bash or sh) and `db`. `unit` and `db` run with `isolate: false`: a worker runs its files one after another in one module graph (importing the code again for each file was more than half the time). So a test leaves no global state behind: it fakes timers and stubs only for itself and puts them back (`vi.useRealTimers()` in its `afterEach`), and a file that mocks a module (`vi.mock`) is `*.isolated.test.ts`, which runs in a graph of its own (lint refuses `vi.mock` elsewhere). The database files run side by side; each has its own database.
- Fixtures that are read-only are built once and shared: `gameDataFixture()` (deep-frozen) and `catalogueFixture()`, whose single instance matters, since the raid bosses' name index (`feedLookupOf`) is built once per catalogue (rebuilding it on every `bosses()` call was most of the unit suite's time).
- Every project's global setup (`test/support/temp-folder-setup.ts`) points `TMPDIR`, `TEMP` and `TMP` at one folder for the run and removes it at the end: tests make their folders with `mkdtemp(tmpdir())` and need not remove them.

## Waiting for work in the background

- No test waits on real time or on a fixed number of turns of the event loop: no `vi.waitFor` / `vi.waitUntil` / `expect.poll`, no sleep, no loop that polls a condition. Lint (`eslint.config.js`, in `*.test.ts` and `test/support/`) refuses `vi.waitFor`, `vi.waitUntil` and `expect.poll`; a `setTimeout` or `setInterval` (by its bare name or as a property, `globalThis.setTimeout`) inside `new Promise` with any delay but a literal `0`; a bare `setTimeout(n)` with a number; and `setTimeout` / `scheduler` of `node:timers/promises`. It does not see a sleep hidden in a helper of another name or a loop over turns: a turn counted by hand (`await new Promise((r) => setImmediate(r))` as a wait) or a polling loop is refused in review. A test that truly needs real time disables the rule on its line with the reason; they are: the reading process of `ocr-service.test.ts` (a real child process, two), the measurement of the event loop in `dm-sender.test.ts`, and the lock waits of real MySQL in four `*.db.test.ts` (the fourth: an opt-out under way while a party's record reads the opt-ins, `history-recording.db.test.ts`). One more check measures the wall clock on purpose, without a sleep: the budget of `placeMap` in `static-map.test.ts` (1 s, against a slowdown by an order of magnitude). So a plan runs its new and changed test files ten times in a row only when it adds a test that must use real time.
- A test awaits the work itself. In this order: the service's own `flush()` / `idle()` / `whenIdle()`; else a count the fake keeps of what it saw (`Tally`, `test/support/tally.ts`: `add()` when it happens, `reached(n)` resolves once it happened `n` times in all, and rejects after `TALLY_LIMIT_MS` with what it waited for and the count it saw, so a broken behaviour fails readably), such as `FakePartyGateway.postEdits(postId)`, `FakeRoleGateway.requests`, `FakeScreenshotReader.readsBegun`, or a named `Tally` in the test's own wrapper of a fake; the timers of the work by `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })` and `vi.advanceTimersByTime*`.
- A test that must see what a run left behind at its end (a timer it asked for, or none), or that nothing has happened while something is held, settles the background (`test/support/timers.ts`): `watchBackground()` fakes `setTimeout` and watches the immediates until the test ends, `watchForTest()` only watches them, `watchEachTest()` (called in a file or a `describe`) watches those of every test, and `watchImmediates()` is the bare watch (`restore()` afterwards); then `await settle()`, which resolves once no `setImmediate` callback (on which the fakes answer) waits any more. It sees only the global `setImmediate` / `clearImmediate` from the moment the watch began: I/O, timers that are not faked and `setImmediate` imported from `node:timers` are invisible to it, so "nothing happened" after `settle()` means something only where the work answers on the global `setImmediate` and `setTimeout` is faked.
- A time limit made with `AbortSignal.timeout` (downloads, requests) is faked by `fakeTimeoutSignals()`: its signals abort only on `expire()` (and are aborted already when made afterwards, so a retry with a fresh limit cannot be tested with it), so a fake that stalls rejects at once for a signal that is aborted, as `fetch` does. A delay that is a setting and is not the subject of the test is 0 (`renamePauseMs`). Time measured with `performance.now()` of `node:perf_hooks` is not reached by vi's `performance` fake: spy on `performance.now` to follow the faked `Date` (`dm-sender.test.ts`, the drain).
- A test builds a moment from a local time with `zonedAt(text, zone)` (`test/support/time.ts`, plan 8Y: `feedTime` of `src/domain/time/zoned.ts`, so `2026-10-24T14:00` is that wall-clock time in `zone`, a time with an offset or `Z` that moment; a time it cannot read throws), wrapped per file or support module as `at(local)` (`test/support/parties.ts` in `PARTY_ZONE`, `test/support/max-bosses.ts` in `MAX_ZONE`). A clock time of today is `zoned(Date.now(), zone).with({ … })`. Never `Temporal.Now`: lint refuses it everywhere, so a faked `Date` holds for every clock.
- `settle()` gives up after 10,000 turns ("the background never settled") and refuses to run when `setImmediate` is no longer the watched one (faked by vi after the watch began); `Tally.reached` gives up after `TALLY_LIMIT_MS` (10 s) and is given up with its test.
