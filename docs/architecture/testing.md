# Testing

Tests are colocated, use real MySQL and real loggers, never the network, and run against strict fakes of Discord. This file lists the helpers and fakes of `test/support/` by area. Read before writing or changing tests.

## The database and the network

- Tests are colocated: `*.test.ts` (unit, no Docker) and `*.db.test.ts` (needs Docker). Test against real MySQL and real pino loggers (`test/support/`) rather than mocks. A run of the database suite starts one MySQL container (`test/support/mysql-global-setup.ts`); `startDatabase()` (`test/support/mysql.ts`) gives each caller a database and a user of its own in it and drops both at `stop()`. The user may also read `performance_schema.data_lock_waits` and `threads`, to see which transactions wait for a lock: a test that has a statement wait for a lock asserts the wait, of its own user's sessions only, since the server is shared: `lockWaitsNow(db, holder?)` (`test/support/lock-waits.ts`) counts them now, and `lockWaits(db, holder)` asks until a transaction other than the holder's (`connectionId(trx)`) waits, every 150 ms, with a deadline of ten seconds. Not `information_schema.innodb_trx` or `processlist`: MySQL 9.7 fails to read them (error 3854) while any statement of the server holds a character beyond three bytes, such as an emoji.
- A database test that a statement draws no warning of MySQL (a deprecated syntax, `DEPRECATED_SYNTAX` 1287) runs it through `lastWarnings(db, work)` (`test/support/mysql-warnings.ts`): `work` in a transaction of its own on one connection, then `show warnings`, which follows its last statement rather than the commit's (plan 8W-3).
- A database test that checks which index a read uses asks `explain format=traditional …` and reads the row's `key` (`board-repository`, `history-repository`, `target-want-repository`): since MySQL 9 a bare `explain` answers in the tree format, one row of text without `key`.
- The plan of a repository's own statement (plan 8Z-2): `planOf(database, (db) => new SomeRepository(db).read(…))` (`test/support/query-plan.ts`) runs the read on a connection that hears every statement and explains the one it asked with the values it was asked with (`plansOf` for a read of several statements, one plan each in the order asked, a transaction's `begin` and `commit` left out, so that a write in a transaction of its own is explained statement by statement: `SavedRouteRepository.removeGym`), so that the assertion follows the repository's real `where` and `order by`; `scanned(plan)` names the tables read whole (`type` `ALL`; the tables MySQL builds itself, `<derived2>`, left out). A plan depends on the statistics: seed enough rows for the optimizer to choose as it does on a real history (thousands, with the shares of a real table: few open rows among many decided ones), then `analyze table`, and say in the test what was seeded. Assert the key, `scanned(plan)` being empty, or a row’s `Extra` without `Using filesort` (a read in the order of its index), never a time.
- A repository's retry after a deadlock (`retryOnDeadlock`) is tested with `deadlockingOnce(db, kind, table)` (`test/support/deadlock.ts`, plan 19B-2): the database whose first `insert`, `update` or `delete` of that table fails as a deadlock (`deadlockError()`, errno 1213) before it is sent, the transaction around it rolled back; `deadlocks()` says it came (`SavedRouteRepository.save`, `GymRemovalRepository.remove`). Older tests make theirs in a hook of their own (`RemovalHooks.step`, the stop reports' `failing`).
- The bot reads the activity buckets through `KeptActivity` (plan 8Z-2), which keeps each read a minute. `activityWebWith` and `regionTalliesWith` take the bare `MemoryActivity`, so that a test sees at once what it added; a test of the kept reads gives the wrapper itself, on its own clock: `new KeptActivity(memory, { now: () => web.clock.now })` as `reader` (`src/web/activity.test.ts`, `setup({ kept: true })`), and counts the database's reads by `MemoryActivity.reads`.
- Tests never use the network. Game data in tests comes from the fixtures built by `scripts/game-data/make-fixtures.ts` (`catalogueFixture()`, `gameDataFixture()`); raid bosses come from `test/support/raid-bosses.ts` (`readRaidBossFeed()`, `raidBossesFixture()`, and `MemoryRaidBossStore` for the service, a `MemoryBossStore` of the raid family). ## How the suites run

- The projects of `vitest.config.ts`: `unit`, `isolated`, `shell` (`*.sh.test.ts`, which start Git Bash or sh) and `db`. `unit` and `db` run with `isolate: false`: a worker runs its files one after another in one module graph (importing the code again for each file was more than half the time). So a test leaves no global state behind: it fakes timers and stubs only for itself and puts them back (`vi.useRealTimers()` in its `afterEach`), and a file that mocks a module (`vi.mock`) is `*.isolated.test.ts`, which runs in a graph of its own (lint refuses `vi.mock` elsewhere). The database files run side by side; each has its own database.
- Fixtures that are read-only are built once and shared: `gameDataFixture()` (deep-frozen) and `catalogueFixture()`, whose single instance matters, since the raid bosses' name index (`feedLookupOf`) is built once per catalogue (rebuilding it on every `bosses()` call was most of the unit suite's time).
- Every project's global setup (`test/support/temp-folder-setup.ts`) points `TMPDIR`, `TEMP` and `TMP` at one folder for the run and removes it at the end: tests make their folders with `mkdtemp(tmpdir())` and need not remove them.

## Waiting for work in the background

- No test waits on real time or on a fixed number of turns of the event loop: no `vi.waitFor` / `vi.waitUntil` / `expect.poll`, no sleep, no loop that polls a condition. Lint (`eslint.config.js`, in `*.test.ts` and `test/support/`) refuses `vi.waitFor`, `vi.waitUntil` and `expect.poll`; a `setTimeout` or `setInterval` (by its bare name or as a property, `globalThis.setTimeout`) inside `new Promise` with any delay but a literal `0`; a bare `setTimeout(n)` with a number; and `setTimeout` / `scheduler` of `node:timers/promises`. It does not see a sleep hidden in a helper of another name or a loop over turns: a turn counted by hand (`await new Promise((r) => setImmediate(r))` as a wait) or a polling loop is refused in review. A test that truly needs real time disables the rule on its line with the reason; they are: the reading process of `ocr-service.test.ts` (a real child process, two), the measurement of the event loop in `dm-sender.test.ts`, and the lock waits of real MySQL in five `*.db.test.ts` (the fourth: an opt-out under way while a party's record reads the opt-ins, `history-recording.db.test.ts`; the fifth: the activity heatmap's adding waiting for a record not yet committed, `activity-repository.db.test.ts`, plan 8H-4). One more check measures the wall clock on purpose, without a sleep: the budget of `placeMap` in `static-map.test.ts` (1 s, against a slowdown by an order of magnitude). So a plan runs its new and changed test files ten times in a row only when it adds a test that must use real time.
- A test awaits the work itself. In this order: the service's own `flush()` / `idle()` / `whenIdle()`; else a count the fake keeps of what it saw (`Tally`, `test/support/tally.ts`: `add()` when it happens, `reached(n)` resolves once it happened `n` times in all, and rejects after `TALLY_LIMIT_MS` with what it waited for and the count it saw, so a broken behaviour fails readably), such as `FakePartyGateway.postEdits(postId)`, `FakeRoleGateway.requests`, `FakeScreenshotReader.readsBegun`, or a named `Tally` in the test's own wrapper of a fake; the timers of the work by `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })` and `vi.advanceTimersByTime*`.
- A test that must see what a run left behind at its end (a timer it asked for, or none), or that nothing has happened while something is held, settles the background (`test/support/timers.ts`): `watchBackground()` fakes `setTimeout` and watches the immediates until the test ends, `watchForTest()` only watches them, `watchEachTest()` (called in a file or a `describe`) watches those of every test, and `watchImmediates()` is the bare watch (`restore()` afterwards); then `await settle()`, which resolves once no `setImmediate` callback (on which the fakes answer) waits any more. It sees only the global `setImmediate` / `clearImmediate` from the moment the watch began: I/O, timers that are not faked and `setImmediate` imported from `node:timers` are invisible to it, so "nothing happened" after `settle()` means something only where the work answers on the global `setImmediate` and `setTimeout` is faked.
- A time limit made with `AbortSignal.timeout` (downloads, requests) is faked by `fakeTimeoutSignals()`: its signals abort only on `expire()` (and are aborted already when made afterwards, so a retry with a fresh limit cannot be tested with it), so a fake that stalls rejects at once for a signal that is aborted, as `fetch` does. A delay that is a setting and is not the subject of the test is 0 (`renamePauseMs`). Time measured with `performance.now()` of `node:perf_hooks` is not reached by vi's `performance` fake: spy on `performance.now` to follow the faked `Date` (`dm-sender.test.ts`, the drain).
- A test builds a moment from a local time with `zonedAt(text, zone)` (`test/support/time.ts`, plan 8Y: `feedTime` of `src/domain/time/zoned.ts`, so `2026-10-24T14:00` is that wall-clock time in `zone`, a time with an offset or `Z` that moment; a time it cannot read throws), wrapped per file or support module as `at(local)` (`test/support/parties.ts` in `PARTY_ZONE`, `test/support/max-bosses.ts` in `MAX_ZONE`). A clock time of today is `zoned(Date.now(), zone).with({ … })`. Never `Temporal.Now`: lint refuses it everywhere, so a faked `Date` holds for every clock.
- `settle()` gives up after 10,000 turns ("the background never settled") and refuses to run when `setImmediate` is no longer the watched one (faked by vi after the watch began); `Tally.reached` gives up after `TALLY_LIMIT_MS` (10 s) and is given up with its test.
- No test asserts speed by the clock (a loaded machine fails it): what guards against a slow way counts the work instead (2026-11-07). `countedCorners(corners, reads)` (`test/support/counted-corners.ts`) gives corners whose latitude and longitude count each read, `countedList(list, reads)` a list that counts the items read by index (cheaper, but what is read of a copy is not counted); past `reads.budget` a read throws, so that a slow way fails at once. The package `wayspot-core` keeps its own small counters in its tests (a text that counts what is read of it: `xml.test.ts`, `kml.limits.test.ts`). A budget is the count measured, with room, against what the slow way would read, and the commit that sets it shows the slow way failing.

The rest of the scripts of the stack (`pine`, `docker/backup.sh`) is checked with `shellcheck -s sh` and a scratch stack (`operations.md`).
