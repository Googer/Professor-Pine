# Professor Pine

Discord bot for organising Pokémon Go raids. It is being rewritten from legacy JavaScript (discord.js-commando, knex) to TypeScript on discord.js v14: one forum post per raid, buttons instead of reactions, slash commands, no privileged intents required.

## Hard rules

- **Push what lands on `main-dev`** (Matt, 2026-11-01), never force. `legacy` is the old bot with its intents patch, for legacy instances: leave it alone. No PRs unless Matt asks. Older docs call today's `main-dev` `typescript-migration`.
- **Nothing of the Wayspot export tool reaches this repository.** Its code, its docs and how it works live only in the private `Googer/Professor-Pine-Wayfarer-Export` (local `../Professor-Pine-Wayspot-Export`). Pine keeps the export format and geometry (`packages/wayspot-core`) and the page that hands the built file out. Branches cut before 2026-11-01 hold the old history with the tool: never push them; start from the current `main-dev`.
- **Never contact Discord unasked.** Do not start the bot (`npm start`, `npm run dev`, or in the Docker stack `./pine up`, `./pine restart`, `./pine update`, `./pine restore` without `--no-start`) or run `npm run deploy-commands` / `./pine deploy-commands` or `npm run emoji:upload` / `./pine emoji-upload` (its dry run reads the application's emoji; `--apply` uploads) or `npm run cutover:check` / `./pine cutover-check` (reads Discord's REST API with the token) unless Matt asks; there is a live production bot.
- **Do not edit or delete legacy JS** (`app/`, `commands/`, `types/`, `index.js`) unless a plan task says so. Production still runs it (the branch `legacy` holds it); it is removed at cutover (the Gantt chart's phase 16).
- Database changes are additive only. `knex_migrations` is read, never written; Kysely tracks its own migrations in `kysely_migration`.

Each phase gets its own plan, written from the spec and executed task by task (superpowers subagent-driven development). A plan is prototyped first on a throwaway worktree (one commit per task); Opus reviewers go through the prototype before the plan is written; the plan's code is generated from the reviewed prototype; implementers transcribe it, and after each task the controller checks that the branch equals the prototype commit (`git diff <proto sha> HEAD -- src test` is empty). Inside a plan an intermediate commit needs only the typecheck, the test files it adds or changes and those its change could break; the full `npm run check`, the build and the database suite run on the tip, once the last task and its fix wave are in. A prototype's fix rounds run only those per-commit checks; the full suites run once on the prototype, on its final tip after the last review round (Matt, 2026-10-27: with over 10,000 tests, a full pass per fix round was most of a plan's suite time). Never run two full suites at once: they time each other out. `npm run check`, `test`, `test:unit` and `test:db` take a machine-wide lock (`scripts/suite-lock/`, a folder in the system's temporary folder shared by every checkout and worktree): a second suite prints whose suite it waits for and starts when that one ends. Run suites only through those scripts, never `npx vitest run` without files; a suite uses half the cores (`maxWorkers` in `vitest.config.ts`). Unit and database files share a module graph per worker (`isolate: false`): a test leaves no global state behind, and a file that mocks a module is `*.isolated.test.ts` (`testing.md`, "How the suites run"). Subagents are the project agents `pine-prototyper` (Opus: prototypes, fix rounds, any fix without ready-made code), `pine-transcriber` (Sonnet: applies a plan's briefs mechanically) and `pine-reviewer` (Opus; high effort for the whole-branch review at the end of a plan). When resuming, read the ledger and `git log` first: tasks with a `complete` line are done.

**Compact between phases.** At every phase or sub-plan boundary (a plan finished and its final review passed, or a new plan about to be written), bring the ledger, the follow-ups file, the status below, the Gantt chart and memory up to date, then stop and tell Matt it is the moment to run `/compact` (or start a fresh session), with a short "where we are / what is next". Do not start the next plan in the same turn.

**Keep the Gantt chart current, task by task.** The page is `docs/superpowers/gantt.html`; its data is `docs/superpowers/gantt-data.js` (JSON after `window.GANTT = `), changed with `npm run gantt` (`scripts/gantt/update.ts`), never by editing the page:

- `npm run gantt -- done <task id> <commit>` right after each task's commit (it takes the commit's time; the task starts where the one before ended);
- `-- status <id> progress` when a task starts;
- `-- planning <plan id> <commit before> [<plan's commit>]` while and after a plan is prototyped and written;
- `-- proto-review <plan id> <first prototype tip> <last prototype tip>` for the part of the planning in which the prototype was reviewed and fixed (drawn hatched, "In review");
- `-- status <plan id> review` while the whole-branch review runs;
- `-- review <plan id> <last task's commit> <last fix commit>` when a plan closes (it also marks the plan done).

A row without dates is drawn right of the now line, so a done task must be dated this way. New rows (a new plan's tasks, a split phase) are added to the JSON by hand or by a scratch script; ids are `<plan>.<n>`, and a sub-plan's name starts with its number (`2E-2 …`). Commit the data file with the work it describes or right after it.

## Conventions

These are the rules that hold in every area. Each subsystem's own conventions are in its file under `docs/architecture/` (see "Area index"); read that file before changing the subsystem.

### Language and tests

- Node 26, TypeScript 6.0.x (not 7: typescript-eslint requires `<6.1.0`), ESM only. Relative imports use the `.js` extension.
- Dependencies stay current (Matt, 2026-10-16): a package added or updated is its latest stable release; Node and MySQL follow their current LTS (MySQL 8.4 in the stack and the tests; Node 26 since 2026-10-28), images included. A version held back is held only for a stated reason (like TypeScript above), and the reason is written where the pin is. `npm outdated` showing anything else is a follow-up to do, not to leave.
- `strict` and `noUncheckedIndexedAccess` are on. No `any` without a line comment justifying it.
- Tests are colocated: `*.test.ts` (unit, no Docker) and `*.db.test.ts` (needs Docker). Test against real MySQL and real pino loggers (`test/support/`) rather than mocks. Tests never use the network. Every helper and fake: `testing.md`.
- Tests load `test/fixtures/settings.json` (`TEST_SETTINGS_PATH`), not `data/settings.json`.
- Commit messages end with a `Co-Authored-By: Claude …` trailer.

### Configuration and Discord

- Secrets come from environment variables (`.env`, see `.env.example`), never from `data/` files. Blank values mean "unset".
- Required intents are `Guilds`, `GuildMessages`, `DirectMessages`. `MessageContent` only when `settings.ocr.passive`; `GuildMembers` only when `settings.autoAssignRole`. Never `GuildPresences` or `GuildMessageReactions`.
- Ephemeral replies use `flags: MessageFlags.Ephemeral`. Things the user did wrong are thrown as `UserError`; the router turns them into ephemeral replies.
- Every message that is more than plain text is a components-v2 message (Matt, 2026-10-15), ephemeral answers included: one container from `src/render/v2.ts`, sent and edited through `discordPayload`, never an embed (`APIEmbed`, `EmbedBuilder`). Detail: `discord-framework.md`.
- Mentions are off by default (`allowedMentions: { parse: [] }` on the client); a send that should ping must opt in with its own `allowedMentions`.
- Component custom IDs are `<kind>:<id>:<action>[:<arg>...]`, at most 100 characters, built and parsed only through `src/discord/custom-id.ts`.
- Every slash command is a `CommandModule` listed in `src/commands/index.ts` (the router and the deploy script read that list); another name is `alsoAs(command, name)`, a short form a command of its own with `formOf`; subcommands are built with `commandGroup` (`src/discord/command-group.ts`). Detail: `discord-framework.md`.
- The router's order is guards, checks, throttle, deferral, `execute`; an unexpected error, or a `UserError` with `givesBack`, gives the counted use back (`said`: the handler answered already). A handler that needs more than three seconds declares `defer: 'ephemeral' | 'public'` and never calls `deferReply` itself; short work declares `defer: 'late'` and answers only through `answer(interaction, payload)` (`src/discord/late-reply.ts`). A use that a guard refused does not count against the throttle.
- Controls are `ComponentHandler`s listed in `src/components/index.ts`, one per custom-id kind; a command's guards do not cover its controls, so a handler has its own `guards` and `throttle`. A press on an answer's controls answers through `pressAnswer`; a control that answers in place of a message uses `showInPlace` / `sayInPlace`, one that answers in a private message of its own `answerApart`.
- Where an interaction came from is read only through `channelContext(interaction)` (`src/discord/channel-context.ts`), a DM by `!interaction.inGuild()`, never the channel cache; `regionChannelOf(interaction, ctx)` gives the region channel.
- Commands are offered in servers only, and for server installs only, unless the definition sets its own `contexts`. A command that depends on a setting has `enabled(config)`; `enabledCommands()` filters the list for the router, `/help` and the deploy script alike.
- Staff commands (those with `default_member_permissions`) are hidden from other members in `/help`, its autocomplete and its error texts.
- A `DiscordAPIError` logged as `{ err }` has its `url` and `requestBody` redacted (the address of an interaction reply contains its token). Log errors under the key `err`.
- The client keeps no message of a DM channel and at most `MEMBER_CACHE_SIZE` members per server (`cacheFactory` in `src/discord/client.ts`): never read a message or a member from the cache and expect it to be there; fetch (`fetchGuildMember(guild, id, true)` for a fresh one).
- Direct messages go out only through `DmSender` (`send(job)` queues and returns, never throws). Never loop over recipients and send: the legacy bot lost its gateway connection that way. Detail: `notifications-and-dms.md`.

### Data

- Snowflakes are strings everywhere, including values read from `BIGINT` columns (the pool sets `bigNumberStrings`).
- `src/db/types.ts` and `src/db/baseline/legacy-schema.ts` are generated. Do not hand-edit them.
- The migrator accepts only a fully migrated legacy database (takeover) or an empty schema (new install) and refuses anything else without writing to it.
- Repositories (`src/db/repositories/`) are the only code that knows column names. They return plain objects: booleans, `{ lat, lon }`, decoded text.
- A repository method that writes in several steps uses `inTransaction()` (`src/db/transaction.ts`), never `db.transaction()` directly, so repositories compose inside a caller's transaction. One that changes one member's rows of a server runs inside `withMemberLocked` (`members-and-roles.md`).
- Geometry in SQL is latitude first: `POINT(lat, lon)` and `POLYGON((lat lon, …))`, as the legacy bot stored it. Build it with `src/db/spatial.ts`.
- Compare a snowflake with the `BIGINT` column `Region.channelId` through `snowflakeParam()` (`src/db/snowflake.ts`, an explicit cast), and never compare that column with a `VARCHAR` snowflake column in SQL: MySQL compares mixed number and string columns as doubles.
- Gym text (`name`, `nickname`, `description`, `notice`) is stored HTML-entity-encoded for the legacy bot; `GymRepository` encodes and decodes it.
- Times are epoch milliseconds in data and Temporal `ZonedDateTime` in `settings.timezone` while computing, made and read through `src/domain/time/zoned.ts` (`zoned`, `localTime`, `feedTime`, the words; never `Temporal.Now`: the clock is `Date.now()` or an injected `now`). What runs in browsers uses no Temporal: the web page (`src/web/client`, whose tsconfig lacks it) and `packages/wayspot-core` (ESLint refuses it). Lint refuses `luxon` and `Temporal.Now` everywhere (plan 8Y). Member-typed times go through `resolvePartyTime` (`src/domain/time/`).
- What is kept in memory with a bound is a `BoundedMap` (`src/bounded-map.ts`, oldest out); a snowflake is recognised by `isSnowflake` (`src/db/snowflake.ts`). A command's help may depend on the settings (`CommandHelp.details` as a function).

### Domain and parties

- `src/domain/` is pure: no `discord.js`, `kysely`, `node:fs`, network, `src/services/` or `src/db/` imports. Domain modules state what they need of a gym or region as small interfaces.
- One path for every fact (Matt, 2026-10-25): a command, a control, the screenshot readers, the DMs and the web map decide a domain fact (which bosses are valid and at which tier, a party's stage, times and ends, event boundaries, counts, who may see or change it) with the same domain function, never a second implementation. A route calls the service path its command uses (as `reportMaxAs` serves `/max` and `POST /api/maxes`); the web page shows what the server computed or imports the pure `src/domain/` module. A fact without a shared function gets one in `src/domain/`, and every caller moves to it. (The screenshot reader once refused Dynamax Azelf that `/max` took: two paths, 85e4249f.)
- `packages/wayspot-core` is pure as well, and stands alone: its modules import no `node:*` module (its tests may), no `discord.js`, `kysely` or `mysql2`, and nothing of Pine outside the package (ESLint refuses it). The modules the Wayspot export tool imports are an interface of the tool (`wayfarer.md`).
- A party (a raid, a max battle, a meetup or a train) is an immutable plain object (`src/domain/party/party.ts`); everything that can happen to it is a pure function that returns a changed party, or `{ ok: false, reason }`, and the very same object when nothing changed. Never mutate a party.
- A party changes only through `PartyStore.update(id, change)` (`src/services/party-store.ts`): one change at a time per party, written to the database first; `change` is synchronous and decides inside the callback. `Party` is a union: narrow it (`isRaid`, `requireRaid`, `isMax`, `isBattle`, `isTrain` …), never cast to a kind. Detail: `parties-and-posts.md`, `trains.md`.

### Text

- American spelling in everything Pine says to members and staff, and in new or changed docs (Matt, 2026-10-18): "meters", "center", "color", "canceled", "-ize"; names keep theirs ("Centre Ave"). Code identifiers and the columns of a file format keep theirs (`GYM_COLOUR`, the report's CSV column `metres`).
- Every distance Pine says to members or staff, on Discord and on the web, goes through `distanceWords(…, settings.distanceUnits)` (`src/render/distance-words.ts`; Matt, 2026-10-25: one unit setting for the map and Discord), never hand-worded units; `src/text-distances.test.ts` refuses them.
- A member is never named by a bare mention in text that does not ping them (a client that has not loaded the member shows "@unknown-user"): a sentence uses `memberText(member)`, the small print of a post `memberByName(member)`, a list `memberName(member)`, and a line about what a train's maker or an anonymous reporter did `doer(party, member)`. Detail: `parties-and-posts.md`.
- Text a member or a feed wrote is shown through `plain()` (`src/render/text.ts`); text that reaches other members' DMs or a spawn report, and every member's name, through `plainNoLinks`, which also breaks bare addresses.

## Gotchas

- With the installed Kysely, `Migrator`, `Migration` and `MigrationProvider` come from `kysely/migration`, not the package root.
- Plan snippets sometimes fail lint as written. Usual fixes: hoist `vi.fn()` into a local const (`unbound-method`); do not call a `void | Promise<void>` guard from sync code (`no-floating-promises`); cast mock call arguments through `unknown`.
- Prettier can move a line out from under an `eslint-disable-next-line` comment; re-run lint after formatting.
- Git on this machine converts LF to CRLF (`core.autocrlf=true`); the warnings on commit are harmless.
- `.idea/` changes are Matt's; never stage them.
- Shell heredocs on this machine fail on apostrophes and mangle backslashes: write files with the Write/Edit tools or a script file, not `cat <<EOF`.
- Git Bash turns an argument that starts with a slash (`/raid`) into a Windows path (`C:/Program Files/Git/raid`): give such task names to the Gantt script from a file, or run it with `MSYS_NO_PATHCONV=1`. A commit title must not start with a slash either.
- A background shell command starts with `cd <absolute path> && pwd`: a relative `cd` in a backgrounded command runs in whatever directory the shell is in (a full check once ran in the wrong checkout).
- A test whose handler reads `Date.now()` must fake `Date` to the fixtures' day (`location.test.ts`), or it fails for good once today passes the fixtures' clock.
- A prototype worktree has a junction to the main `node_modules`: remove the junction first (`cmd //c rmdir var\proto-x\node_modules`) and check that it is gone, then the worktree; `git worktree remove --force` follows the junction and empties the main checkout's `node_modules`. `npm ci` brings it back (it skips the install scripts of esbuild, onnxruntime-node, protobufjs and ssh2 under npm's allow-scripts policy; the check, the build and those packages work without them; sharp has none since 0.35).
- Never open `.env` (it holds the bot token); check a value only with a command that reports set or empty, and change one only with a script that prints no values.
- The Write tool turns a `\uXXXX` escape of an invisible character (U+202E and the like) into the raw character; check such test strings afterwards (`scratchpad` script or grep) and keep them as escapes.
- An implementer handed finished code tends to skip the failing-test step: tolerable for transcription, but fix rounds without ready-made code must show RED first.
- A staging script that wires its own client must use `createClient()`, wait for `ClientReady` before any gateway call and load in the order of `src/app.ts`; earlier ones are in the git-ignored `var/stage/`.
- Folding review fixes into prototype commits (`commit --fixup`, autosquash): never split a file that several tasks touch by hunks (zero-context hunks cut blocks apart and intermediate commits stop compiling). Build its version for each commit by three-way merge, `git merge-file --ours <file at that commit> <file at the old tip> <file at the fixed tip>`, check what it kept of later tasks, recreate the commits, then run the check on every commit.
- The controller must not commit in the checkout while an implementer works there: a commit takes everything staged, also the implementer's files. Wait for the implementer, or commit with `git commit -- <paths>`.
- No test waits on real time or a counted number of turns: it awaits the event itself (`Tally`, `watchEachTest().settle()`, fake timers by the timer count); lint refuses `vi.waitFor`, `expect.poll` and sleeps in tests (`testing.md`, "Waiting for work in the background"). Only a plan that adds a test that must use real time runs its new and changed test files ten times in a row before it closes.
- Docker Desktop on this machine can lose its IPv6 port forwarding: `localhost` goes to `::1` and is closed at once, so every database test fails with "Connection lost: The server closed the connection" while `127.0.0.1` works. Run `TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1 npm run test:db`, or restart Docker Desktop.
- A change of the screenshot reader (`src/domain/ocr/`, `src/ocr/`) is checked on real screenshots before it is committed, not only by the unit tests (which draw lines, never run the models): `ocr:check` of the research samples against the committed baseline and of every labelled folder under `var/ocr/matt-*` against its own (`.v2.json`), as the skill `improve-screenshot-reading` says (step 4); a sample from right to wrong is a failing test (2026-10-24: skipped once, run after).
- The Linux-only test of the reading process's thread priority runs in a container: `git archive HEAD | MSYS_NO_PATHCONV=1 docker run --rm -i node:26-slim sh -c 'mkdir /work && cd /work && tar -x && npm ci --ignore-scripts && npx vitest run --project unit src/services/ocr-service.test.ts'`.
- `npm run check | tail` hides a failure: look at the exit status (`npm run check > log; echo $?`).
- The built-in browser's preview shows a local page as a snapshot that cannot load a second local file (the Gantt chart's data): serve the folder with `python -m http.server` on 127.0.0.1 in a tab of its own, and stop the server afterwards.
- A subagent may be refused when it writes a report as a `.md` file: ask for the report in the reply, and save what must be kept yourself.
- An implementer may apply a brief's code blocks with a script (`git apply` for the diffs) instead of typing them, when the brief is the only source and the transcription diff is empty.
- Scratch `.ts` files anywhere under the checkout, also in the git-ignored `.superpowers/`, are covered by `eslint .` (Prettier skips `/.superpowers/` and `/.claude/worktrees/`, `.prettierignore`): give them another extension when they are not being run.
- `.prettierignore` entries for the legacy directories are anchored (`/commands/`): an unanchored `commands/` also hides `src/commands/`.
- `npm run db:codegen -- --verify` compares with the working copy of `src/db/types.ts`, which git checks out with CRLF here, so it reports every line although the committed (LF) content is current. Verify against `git show HEAD:src/db/types.ts`, or trust the migrator's db test.
- The unit project's `testTimeout` is 15 seconds and the database project's five minutes (`vitest.config.ts`), so that suites running side by side do not time each other out (a migrator test builds whole schemas in about twenty seconds). A unit test that needs seconds by itself is still a fault to look into.
- `@pine/wayspot-core` (`packages/wayspot-core`) is read from its sources only under the condition `pine-source`: the typecheck (`customConditions`), Vitest (`ssr.resolve.conditions`), esbuild (`conditions`) and every `tsx` script in `package.json` (`--conditions=pine-source`) set it, and so do the threads and processes started from a `.ts` file (`save-check.ts`, `ocr-service.ts`). Without it Node takes the package's `dist/`, which only `npm run build` makes: a `tsx` or `node --import tsx` run without the flag fails with `ERR_MODULE_NOT_FOUND` for `packages/wayspot-core/dist/…` only while that folder is absent; after a build it runs silently on the compiled package as it was at that build, however the sources have changed since.
